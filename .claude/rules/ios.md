# iOS App Conventions

## HealthKit
- Workout sync: HealthKit -> WorkoutProcessor -> WorkoutSyncService -> Backend API
- Every automatic upload trigger (observer, foreground, BGTask, launch) funnels through `syncNewWorkouts`'s `guard !isSyncing`: the flag must clear via `defer` — a rethrow once stranded it true, starving ALL sync for the process lifetime ("dashboard done, friends list 0.00, posts 403 until Sync Streak"). Its incremental filter scans 48h BEHIND `lastSyncDate` (uploaded-ids set dedupes, watermark is monotonic) — strict `endDate > lastSync` permanently dropped late-landing Watch workouts, same trap as WorkoutIndex.
- A workout's LOCAL DAY is `Calendar.current.startOfDay(for: workout.startDate)` and nothing else (`HealthKitManager.localDay(for:)`) — the same rule the server files `local_date` under, so every bucketing surface (calendar, insights, profile grid, `cachedWorkouts(onLocalDay:)`) must use it or the app draws an empty day the server is counting. `WorkoutProcessor.determineLocalDateWithOffset` used to "correct" any workout outside 6 AM–10 PM by brute-forcing offsets −6…+6 until one landed in "reasonable" hours AND changed the day: −6 was tried first, so EVERY midnight-to-5 AM walk filed itself under the previous day and displayed 6h early. It consulted no timezone, no location and no `HKMetadataKeyTimeZone` — a real timezone change is already in `Calendar.current`, and `Date` is absolute, so `localEndTime` adding those hours applied the device offset twice. Never "correct" an HKWorkout's clock. `localDate`/`localEndTime` are PERSISTED in the `WorkoutIndex`, so a write-side fix needs the `version` guard in `WorkoutIndex.load()` bumped or existing installs keep the shifted cache forever. Also never reconstruct a start as `end - workout.duration`: duration is pause-EXCLUDED, so it lands after the real start on any paused walk — use `workout.startDate`.
- HealthKit builders must take the app's long-lived store (`HealthKitManager.healthStore`), never an inline `HKHealthStore()`: the store has to outlive every operation started on it, and a dropped one reports nothing — the symptom is a walk that saves fine with no map in Apple Fitness OR our feed. Route writes fail silently in three distinguishable ways and the logs must say which: nothing captured (accrual gates), batch rejected, or the Route switch denied in Settings > Health > Data Access (`isRouteSharingDenied()`; separate from the Workouts switch). `insertRouteData` demands STRICTLY ascending timestamps and rejects the whole batch otherwise — route points round-trip through `JSONEncoder.dateEncodingStrategy = .iso8601`, which drops fractional seconds, so two points kept inside one second (routine at running pace) come back equal; `WorkoutRouteCleanup.strictlyAscending` is what re-establishes the precondition. A route point must carry the fix's MEASURED MOTION, not just its position: `WorkoutRoutePoint` persisted 6 fields and dropped `speed`/`course`, so every location written to HealthKit reported `-1` (CoreLocation's "invalid") on all four motion fields — our own maps read only `.coordinate` and drew fine, while Apple Fitness, which plots a route BY its speed, showed the walk with no map at all. Rebuild a `CLLocation` only via `withCoordinate`/`withTimestamp` (WorkoutRouteCleanup): the `course:speed:timestamp:` initializer sets `courseAccuracy`/`speedAccuracy` to -1, and a negative accuracy invalidates the very value you were preserving. Already-written routes can't be repaired — the samples are in HealthKit without it. A phone-built workout also carries NO calories: `HKWorkoutBuilder` aggregates only what you `add` (the Watch gets real energy from `HKLiveWorkoutDataSource`; the phone has no sensor for it), so active energy is written explicitly — `WorkoutEnergyEstimate`, the ACSM equations minus rest, collapsing to `0.005 · c · metres · kg` with `bodyMass` read from Health. It rides the DISTANCE batch: `add` accepts or rejects a batch as a UNIT, so check `isActiveEnergySharingDenied()` first (Active Energy is a separate switch from Workouts, and an unasked sample for a denied type costs the walk its distance) — and never split it into a second `add`, which is a second completion the finish chain can never return from, leaving the workout for the 10s timeout to clean up as unsaved.
- HealthKit queries ERROR when the device is locked (protected data). Never treat a query error as "0 miles" — only a successful empty result is a real zero. Writing 0 on error randomly reset widgets.
- Feed route maps are read from HKWorkoutRoute at sync time. In-app tracked workouts must write their GPS trace via `HKWorkoutRouteBuilder.finishRoute` after `finishWorkout` (and `HKSeriesType.workoutRoute()` must be in the SHARE auth set) — points buffered in InProgressWorkoutStore alone never reach the backend. AND the HealthKit observer fires on `finishWorkout` itself, BEFORE the route exists — that raced sync uploads route-less and marks the workout synced, so the feed map never appears while Apple Fitness (reading HealthKit directly) shows it fine. The finish must call `WorkoutSyncService.uploadWorkout(withId:)` after `finishRoute` lands — safe both ways because `workout_routes` only upserts when a payload HAS a route (fullSync/recalibrate re-pushes never erase routes).
- A route polyline drawn OVER an `MKMapSnapshotter` image must be projected with `snapshot.point(for:)` — never a linear lat/lon→pixel map of the requested `MKCoordinateRegion`. MapKit EXPANDS the region to fit the requested image aspect, so the region never describes where a coordinate landed; and the image is displayed `.aspectRatio(.fill)`, so a snapshot whose size doesn't match the view is scaled+cropped while the line isn't. `WorkoutRouteMapView` requested a fixed 400×300 for a 4:5 card and stretched every track ~1.7× horizontally — a shoreline walk drew out in the bay while Apple Fitness (same HKWorkoutRoute) was fine. Snapshot at the view's own size and pass `RouteMapSnapshot` (image + size + projection) to anything compositing it. `RunPostService.renderRouteImage` was always right; compare against it. DRAWING it on is a second trap: a `Shape`'s `.trim` animates INSIDE the shape, so the parent body sees the driving `@State` exactly twice — at 0 and at 1 — and any expression on it is evaluated at those two endpoints only. A per-line `min(1, trim * pace)` therefore staggered nothing (both endpoints identical) and `if trim >= 1 { endMarker }` put the end pin on screen the instant the draw was SCHEDULED. Per-line timing belongs in `.animation(_:value:)` on each line (set the state OUTSIDE `withAnimation`, or the enclosing transaction overrides every delay and welds the crew back together); anything that must vary DURING the draw has to be a second animated property, not an expression — the drawing bead is a second `.trim(from: t - k, to: t)` whose window slides for free. And a change made in the same update as `trimProgress` inherits that line's curve, so a start pin dropping alongside it needs its own update (a short sleep between). Crew colours come from `CrewRoutePalette.companionColors(count:avoiding:)`, never `color(at:)` — `avoiding:` is what keeps the first companion off the author's activity accent, which drew blue-on-blue for every walking buddy card.
- WidgetKit renders statically: `.onAppear`-driven `@State` animations never play in widget views — render entry values directly (for a day-walk, bake per-hour `Timeline` entries — that spends NO reload budget). `WidgetDataStore` data is day-stamped; `load()` returns zeros for a stale day, and saves skip no-op writes (widget reloads are budgeted per day). The widget process can't read `UserDefaults.standard` — any app pref a widget needs (e.g. dashboard style for `StreakFlameWidget`) must be mirrored into the App Group via `WidgetDataStore`. New widget files go in `app/MileADayWidgets/` (a synchronized folder — auto-joins the widget target, no pbxproj); `app/Mile A Day/Widgets/` files need pbxproj membership.
- Dashboard style uses `dashboardStyleV1` / `dashboardStyleChosenV1`: Modern is the default. Both dashboard heroes share the flame lifecycle (`StreakFlamePhase` + `StreakFlameClock`): coal at streak 0, burning shrinks with time left (SIZE signals time — never fade opacity), blazing when done. Only dashboards pass `phase:`/`dayEnd:` into `FlameBuddyView` — legacy callers (chooser preview, Live Activity `FlameBuddyFigure`) stay phase/vigor-less to keep the old stage look, and static buddy code must stay copied in both widget locations when Live Activity visuals change. The goal celebrations' `ReignitingFlameView` takes a `FlameRevivalOrigin` derived from the streak — `.coal` ONLY when the flame was actually out (streak <= 1); both views hardcoded it, so a 400-day streak was told daily that it had died and been revived. NEVER animate a flame by opacity-crossfading two `FlameBuddyFigure`s: they wobble on different curves and each draws its own glow + ground shadow, so the pair ghosts apart mid-fade and reads as a second flame appearing and going away. Warm ONE figure instead — `FlameBuddyFigure(blaze:)` blends the live vigor palette/glow/core into the `.blazing` look (`FlamePalette.outer/inner(vigor:blaze:)` resamples the 3-stop live gradient to the blaze's 4 stops so nothing pops at blaze 0). Its `SadEmberBuddy` is the only face the Modern side can ever draw, so it must honour `showsFace`. Both heroes' stat lines are ONE `HeroStatColumn` (DashboardModeCards) — they drifted to different stats when forked. The flame WIDGET mirrors the hero's streak box + savers chip (`FlameStreakBox`) from `WidgetDataStore` values. A value that moves all day must not reload on every write or it spends the whole budget on itself: `save(todaySteps:)` stores EXACT but only reloads per 1000-step bucket, and it's monotonic-within-day because `todaysSteps` reads 0 on a FAILED HealthKit query (locked device). `save(longestStreak:)` never reloads at all — the `save(streak:)` beside it carries one. NEVER predict a widget's usable height — a medium widget's is far below what the 170pt frame and documented content margins imply (measured under 119pt on a Pro Max), so a third stat row sized by arithmetic vanished twice. DERIVE the layout from a `GeometryReader` height (`FlameColumnMetrics.fitting`) and never let a `ViewThatFits` candidate differ in CONTENT — a wrong prediction then silently deletes a row instead of just tightening it. To measure an existing widget from a screenshot: a centred column's height is `2 * (85 - topInsetPt)`. A child taller than the canvas (a fixed-size flame) makes the HStack taller than the canvas and corrupts any GeometryReader beside it — give it `maxHeight: .infinity` and let it overflow visually.
- NO widget may poll the clock with `.after(interval)`. Its data only moves when the app writes it (which force-reloads that kind), so the ONLY scheduled reload is `.after(MADWidgetClock.endOfDay())` — five widget kinds at 30-60min policies asked ~126 reloads/day against a ~40-70 budget, and an over-budget kind has ALL its reloads dropped, the app's included, so the widget freezes while the app is right. Clock-driven state instead comes free from `MADWidgetClock.hourlyEntryDates()` (hour-ALIGNED, so the 6 PM at-risk switch fires on time) plus a baked midnight entry so the day rolls over even if that one reload is dropped. Never bake a countdown STRING into an entry — an entry can sit on screen for an hour ("7h 24m left" vs the app's "6h 30m"); use `MADWidgetCountdown.text(to:)` (`Text(_:style:.relative)`, which the system re-renders itself).
- Background HealthKit reads must gate on `hasLoadedInitialData`, not a fixed sleep — on a locked device queries error, `retroactiveStreak` reads 0, and `updateFromHealthKit` persists it unconditionally (streak 0 stuck in widgets). `MADBackgroundService` must also use `UserManager.shared` / `HealthKitManager.shared`, never its own instances: a private `UserManager()` decodes `currentUser` once and never sees the app's later writes, so every background sync re-persisted that frozen copy (`updateFromHealthKit` assigns the streak unconditionally, `vettedHealthKitStreak` vets against the stale value) — the widget sat days behind a correct dashboard. And its `checkForMileCompletion` must NOT call `completeRun`: `updateUserWithHealthKitData` already stamped `lastCompletionDate`, so it only re-adds today's miles to lifetime `totalMiles`.
- WorkoutIndex incremental updates need the 48h lookback + record-id dedup: querying strictly from `lastUpdated` permanently drops workouts that reached HealthKit late (Watch sync), leaving a `qualifyingDays` hole — `activeStreak()` stops there and the dashboard flashes a tiny streak until the backend rescue lands. Backend-streak ≫ local triggers a debounced rebuild (`repairWorkoutIndexIfStale`).
- The displayed streak (`currentUser.streak`) is quarantine-gated: `UserManager.vettedHealthKitStreak` refuses 2+ day drops from local recomputes unless the backend (48h-fresh, recomputed server-side every `getUserStats`) agrees or a same-day full index rebuild confirms. Never write `hk.retroactiveStreak` raw to UI/widgets/watch — it flaps on index holes; route through `updateUserWithHealthKitData` / push `max(hk, user.streak)`.

- Apple NEVER reports HealthKit READ authorization — a denied read is an empty array, identical to a day with no walks — so `HealthAccessMonitor` only claims what it can prove: per-type WRITE status (`authorizationStatus(for:)`, exact), and "has every type been ANSWERED" (`getRequestStatusForAuthorization` == `.shouldRequest`, exact, and the case that catches a type added by an update). Reads are labelled unknown in those words; guessing is worse than saying so. `requestAuthorization` re-prompts ONLY for un-answered types, so the in-app "Grant access" button is offered on `.needsRequest` and never on a denial — there it would do nothing when tapped. There is also no public deep link to an app's page in Health (Apple has never shipped one): `x-apple-health://Sources/` reaches Sharing ▸ Apps and degrades to Summary if unrecognised, so the last two taps are spelled out on screen. `HealthKitManager.healthKitReadTypes/WriteTypes` are non-private so the screen can't drift from what the app actually asks for.
- ONE settings page (`MADSettingsView`), pushed by BOTH the Dashboard and Profile gears — there were two, and half the app's settings were only reachable from a tab you might never open. It owns its own alerts/sheets and its own account actions: a modal attached to the view that PUSHED it can't present while it's on top (that's why Sign Out once read as a no-op until you hit Back). Anything the Dashboard used to hand it via a closure (the goal sheet) moved WITH it — leaving the sheet behind creates one nothing can present.
- `PostGridFilter` is `all`/`collabs` only; profile photo-first curation is the account-level `auto_posts_on_profile` setting, not a sticky visitor-side filter. The server still honours `photos`/`auto` for shipped builds, and a preference persisted as one of them decodes nil ⇒ `.all`, so nothing stays stuck filtered. `PostGridPreferences` (sort/filter/density) and pins apply to the OWNER's grid only; a visitor's copy of someone else's profile always draws the defaults, or a sticky filter carried onto a stranger's profile reads as "they've posted nothing". A filtered-empty grid must say which filter did it. `PostItem.pinned_at`/`coauthor_on_feed`/`include_route` and `PostCoauthorItem.on_feed`/`include_route` are all nil on older servers — branch on nil to mean "not offered", never "off". FeedEntry has explicit CodingKeys: every one of those added there needs a case.
- The FIRST-RUN Apple Health import is minutes of work and every part of it must say so. Its cost is TWO HealthKit round-trips PER WORKOUT (`SplitCalculator` + active energy), so `workoutDetails` runs them 6-wide (`withTaskGroup`, slotted back by index — payload order unchanged) and every store is LONG-LIVED: a per-call `HKHealthStore()` is released before its query answers, the same silent-nothing trap as a dropped workout builder. Progress must report `preparedCount` (per WORKOUT) not just `uploadedCount` (per batch of 50) or the bar stands still for a minute and reads as frozen, and a RESUMED import reports against `fetchedWorkouts.count` with `completedBeforeRun` set — totals over what's LEFT restart the bar at 0% and read as "it lost everything". NEVER surface a HealthKit `localizedDescription`: `HKError` code 4 localizes to "Authorization not determined", which is not a diagnosis (Apple never reports READ auth) and only ever means "we asked before the sheet was answered" — classify through `SyncFailure` instead. Retry belongs to `retryFailedSync()`, not `startInitialSyncIfNeeded()`, which no-ops both while syncing and once `lastSyncDate` exists — i.e. exactly when someone taps retry. And nothing may draw a conclusion from the history mid-import: the streak reveal is gated on `isImportingHistory` and re-armed off `MAD_InitialSyncCompleted` (a notification, never observing the service — its progress publishes once per workout and would redraw the dashboard thousands of times).
- A vertical `ScrollView` scrolls HORIZONTALLY whenever its content overflows — the axis argument only governs bouncing, and a UIScrollView rubber-bands far past its content, so a few points of overflow become ~100pt of travel and every vertical drag picks up a wobble. `.lockedToScrollWidth()` (ScrollAxisLock) goes LAST on the scroll CONTENT, after its own padding, never on the ScrollView. It's applied to the full-bleed card screens (both profiles, Workouts, Feed, Friends, Inbox) where it's visually a no-op; do NOT add it to a scroll whose content VStack is `alignment: .leading` and narrower than the screen, which it would left-align. It is not a licence to stop fixing the overflow — a clipped row is still a bug, just a quieter one than a shaking screen.
- The referral catalog is THREE files that must move together: `PersonalizationView.referralOptions` (iOS), `REFERRAL_SOURCES` (usersController — anything off-catalog is silently rewritten to `other`, so a chip the server doesn't know is a chip whose data you never see), and `SOURCE_LABELS` (admin Growth.tsx). Sources whose `referral_detail` names a PERSON rather than a channel live in `PERSON_REFERRAL_SOURCES` (userService, imported by both admin services) — the attribution graph filters on it, so a new person-source not added there is invisible in the one panel that answers "who is bringing people in".
- A streak's date range must show the START year whenever the end carries one or the two differ. Suppressing it unconditionally rendered a 408-day run as "Aug 15 – Sep 26, 2025" — six weeks — so the app appeared to contradict its own headline number, which is what makes a user read their history as a data bug. `StreakStartExplainer` is the answer to "why does it start there": it names the missing day from `StreakErasStore` (current era start, previous era end) rather than leaving the number unfalsifiable.

## Key Patterns
- Profile screens (own `ProfileView` + friend `UserProfileDetailView`) are composed from `ProfileHero.swift`: full-bleed banner (uploaded photo else a `ProfileBannerStyle` gradient preset — app colours only, unknown/nil resolves to `.ember`), the avatar in today's goal ring (orange in progress → green done; `progress` nil draws the bare track, never 0%), `NextMilestoneChip` (the next mile MEDAL: `MileMilestones` reads the `miles_*` badge thresholds — pass the loaded badge list so it matches the Total Miles screen's "Next Medal"; nil total ⇒ hidden — a stranger's profile must not read "25 mi to go"), `ProfileStatTiles` (Streak · Miles · Friends; the streak tile turns GREEN on `streakDoneToday`, the same rule as the ring — own profile derives both from `ownGoalDoneToday`), the token shelf (own profile, directly under the tiles), and the underline `ProfileTabBar` (Activity first — the Activity tab carries only the daily-goal row, never the streak number again). The ring hangs off the banner by PADDING, not offset. The friend screen re-fetches `GET /users/:id` on appear (`fullUser`) because list/feed projections carry neither bio nor banner. Banner edits live in `EditProfileView`: a picked photo uploads via `ProfileImageService.uploadProfileBanner` (downscaled first, phone-only), a preset PATCHes `profile_banner_style`, and removal PATCHes `profile_banner_url: null` — the PATCH can only ever CLEAR the path.
- Post cards (`PostCardView`, mirrored by `ActivityCardView`) have TWO media faces behind the PHOTO | MAP toggle (photo leads; "STATS" when the second face is the indoor card — never "indoor"): `photoSlides` (lock → photos → crew photos) and `mapSlide` (route with `RouteStatsOverlayView`'s bottom band, or the indoor card). The toggle and the FLYOVER chip are overlaid on the media CONTAINER, after every slide's `.instagramZoomable`, or the zoom host eats their taps; the crew legend shows only on the map face. The flyover entry is ONE component everywhere (`FlyoverChipButton(accent:)` — a filled pill in the workout's colour with a white play disc, on BOTH faces of a post, raw workout cards, the walk detail and both workout detail sheets): the black glass chip it replaced was only found by people who already knew about the feature. Walks Together tiles are 4:5 in a horizontal ScrollView (a squeezed HStack crops photos) and show the walk's route line (read off its post) when there's no picture; the history strip is the feed's 4:5, never 4:3. Stats moved off the card body: distance + role framing ride the header subtitle ("Walk · 1.08 mi · 2d"), the streak is the footer's orange chip, and `RouteStatsOverlayView` (also BAKED into auto posts by RunPostService) is bottom-band only — nothing up top.
- The two faces are ONE `TabView(selection: $mediaPage)` — photo pages first, the map last — so a swipe and a PHOTO | MAP tap can't disagree (`currentFace` is read off the page, never stored). Self-hypes are allowed on posts AND raw workouts (server too): never gate the clap or the double-tap on `is_self`/`isMine`, and the hype COUNT is its own button opening `HypersListSheet`, whose rows must be wired with `onSelectUser` (dismiss first, then set the profile — `pendingProfileUser`) on every host or the list is dead. Dashboard streak rung: `DashboardMilestoneBar` is the ONE drawing (heroes + `DashboardCards`), titled STREAK MILESTONE over a row of DAY notches (one per day of the climb from `StreakMilestone.previous(before:)` to the next rung, capped at 12) with a "Day 4 of 7" caption — a continuous capsule under the mile numbers read as a second distance bar, and a marker on it overflowed into the labels below, so neither comes back; the profile's chip says NEXT TOTAL MILES MILESTONE for the same reason. Activity-tab blocks share `profileCard()` + `ProfileCardLabel` (Hall of Streaks, Recent Workouts, Walks Together, Recent hypes all converted) — no `madLiquidGlass` there — and the LABEL GOES INSIDE THE CARD: a caps label floating above its own card (Walks Together shipped that way) reads as a stray heading beside the others. Stats-tab cards (Performance, Race PRs, Ghost Races) are the glass card + headline header. A custom toolbar back button is a BARE chevron: iOS 26 wraps toolbar items in its own glass capsule, so a chevron with a circle of its own reads as two stacked buttons.
- A past buddy walk opens as ONE screen, `BuddyWalkDetailView`, from every surface (history card — photo strip AND details — and the Walks Together tiles); the photo used to open the post and the details the recap, and "why do the top and bottom of the card go different places" was the first question. With `walk.postId` it renders the walk's shared post via `PostCardView` (all crew photos in the carousel, everyone's line on the MAP face, flyover, hypes/comments — the feed's exact card, fully wired); without one it fetches each participant's route (`workoutId` + `hasRoute`, consent-gated server-side) and draws them with `RouteArtView` + a crew `FlyoverLaunch`. `BuddyWalkParticipant.finalDistanceMiles == nil` means their phone never synced a workout — the crew card says "not synced", and `BuddyRecapView` only shows its "syncing" spinner while `mayStillSync` (ended < 2h ago); an August walk was spinning in September. `BuddyWalkPhoto.id` is post+user now that a post carries the crew's slides (`is_crew`).
- Flamey's face is DISCRETE: the blink is a 12 fps frame toggle, never an animation. A `repeatForever` animation started INSIDE `onAppear` (the idle bob, the mood hops) attaches to the view's initial commit and every later layout change in the subtree inherits it — the eyes opened as a slow overshooting stretch, taller than the sunglasses covering them. Start those on the next turn (`DispatchQueue.main.async`) and keep `face`'s `.transaction { $0.animation = nil }` in `FlameBuddyFigure`; the widget copies of the figure render statically and don't need it.
- `FreshPostWindowManager` gates posting in TWO tiers and they are not interchangeable: `canPostToday` (a qualifying walk/run landed today — gates POSTING, all day) and `isCameraOpen` (10 min from that workout — gates CAPTURE only). Gate an affordance on `canPostToday` unless it literally opens the shutter; the countdown ring/pill is `isCameraOpen`. Nine surfaces read them and must stay in sync: the feed FAB (unlocked = day, ring = camera), `StoriesRailView.canPost`/`windowOpen`, `SocialFeedView.handleCompose`, `BuddyRecapView`, `PostRunPhotoPromptView` (swaps its primary button to the library when the camera closes; only a day with NO qualifying workout auto-skips to the `is_auto` card), `PostComposerView` (`cameraAllowed` — placeholder, "Change" menu and `autoOpenCamera` all follow it), and the "Add to feed" promote in `StoryViewerView` + `ProfilePostsGridView`/`WorkoutDetailView` (day tier; that promote is a PATCH, not createPost — the easy one to miss). Every create declares `photo_source` (`PostPhotoSource`): `.camera` ONLY for a shot taken in this composer session — a mid-run snap and a promoted story are `.library`/`.existing`, or the countdown rejects a photo whose claim to the walk is its timestamp. Anchors to OBSERVATION time, not `HKWorkout.endDate`, so a late Watch sync gets a full camera window — which also means a workout the app never saw records nothing; `syncPostWindow()` adopts the server's via `GET /posts/window`, gated on `photo_open` NOT the countdown (the usual case is a morning walk this device never saw; adopt-only — never shortens or closes the camera). A workout that already spent its 10 min never re-anchors (`anchoredIds`), or a re-observed workout resurrects a closed window. Both tiers read the wall clock/day stamp, so nothing locks at expiry on its own — that's `scheduleExpiryTick` plus `refresh()` on foreground (which also handles the midnight rollover). The "FRESH" chip is GONE; `is_fresh`/`posted_fresh` stay on the wire for pre-gate builds only.
- Backend `timestamptz` serializes WITH fractional seconds (`…:15.600Z`) and `APIClient`'s decoder uses `.iso8601`, which CANNOT parse those — one bad date fails the WHOLE payload. Type backend timestamps as `String` in DTOs and parse with `[.withInternetDateTime, .withFractionalSeconds]` (see `BuddyDate`); only `date` columns are safe as plain strings.
- Any "did they hit the mile today" SCORING check is `ProgressCalculator.isGoalCompleted(current:goal:)` (0.95 tolerance, mirrors backend `DAILY_GOAL_TOLERANCE`), NEVER a raw `>= goal` — a strict compare renders a completed-per-server day as orange/incomplete (`Last7DaysChart`, the friends hero card, `hasCompletedGoalToday` all had it). EXCEPTION: the in-workout celebration/goal-alert fires at the full goal — see the tracking bullet. Competition goals are a DIFFERENT threshold — server-scored exactly; don't sweep those into the tolerance. Clamp the goal `> 0` first: the helper is `current >= goal * 0.95`, vacuously true at goal 0. A surface showing a DAY's miles reads `healthManager.countedMiles(onLocalDay:)` (deduped, with the index fallback) and lists only `WorkoutDedup.breakdown(in:)`-approved workouts — `ChallengeCompletionDetailSheet` summed the raw `workoutIndex` instead, so a day with a cross-app duplicate listed the same walk twice and totalled more than the dashboard did for that date.
- NEVER read `HKWorkout.totalDistance` for anything a user sees or that gets summed — use `workout.madDistanceMiles` (HealthKitManager.swift, so the Watch target sees it). It floors a walk at `TrackedWorkoutLedger`'s receipt: the exact number `liveDistance` showed when Finish was pressed, stamped in `finishWorkout`'s completion. Without it the tracked number was handed to HealthKit and thrown away, so five pipelines each re-derived the distance and any of them could come back LOWER ("0.34 while walking, 0.22 once it saved"). `HKWorkoutBuilder.add`'s error was discarded (Workouts share access granted + Walking+Running Distance denied ⇒ a workout with no distance, silently); `needsNewWorkoutFetch()` holds `cachedWorkouts` fresh for an HOUR, so the Workouts screen summed a day missing the walk that just ended (`invalidateWorkoutCacheFreshness()` before the post-save fetch); and `WorkoutDedup` could vote it out. A tracked workout now ranks above everything in `duplicateSources` and is never excluded. The receipt is a FLOOR (`max(HealthKit, tracked)`) — but a distance the USER typed on the edit screen (`TrackedWorkoutLedger.userOverride`) is the ANSWER, so it wins in both directions: under `max` a downward treadmill correction read back as the recorded number on every screen AND was re-uploaded over the edit the server had accepted. Its `userChosen`/`tracked` flags are Optional because the ledger is a persisted Codable blob. Sync uploads `madDistanceMiles` too, or the server disagrees with the phone.
- `WorkoutDedup.exclusions` runs duplicate detection over what the CONSENT pass left (`breakdown(in:)` — use it, not the two calls separately): handing `duplicateSources` the full array let an un-approved copy be the keeper, marking the approved one `.duplicate` while the keeper stayed `.sourcePending` — the walk left the total twice and landed in it zero times. And source consent is grandfathered by a TIMESTAMP (`isBeforeGrandfatherLine`), not just a bundle-id sweep: that sweep reads `recentWorkouts`, filled by a separate async query that answers nothing on a locked device, so a source missed in that instant silently subtracted itself from every daily total thereafter. Explicit `.ignored` still outranks the line.
- A per-day chart must take the profile OWNER's `goalMiles`, not a hardcoded 1.0 — `Last7DaysChart` painted a 2-mile-goal friend green at one mile.
- Use `@Observable` (iOS 17+ Observation framework) for new view models.
- Feature views live in `Views/<FeatureName>/` subdirectories.
- Shared UI components in `Views/Components/`.
- Watch app is a separate target at `Mile A Day Watch App/`.

## Auth / Session
- "Who am I?" is the access token's `sub` (`TokenUtils.subject`), never a cached id. Self-scoped URLs are built from `UserManager.currentUser.backendUserId` / `UserDefaults["backendUserId"]`; when those drift from `sub` the server answers **403**, and `APIClient` only recovers on 401 — the app stays "logged in" with friends + daily challenges dead forever. `SessionIdentity.enforce()` (launch, foreground, and on 403) is the only thing that catches it. Never blanket-sign-out on 403: it's also "not friends"/"admin only".
- Two people on ONE Apple account cannot have two MAD accounts — `/auth/signin` resolves the user by EMAIL alone (`apple_sub` is written at creation, never used for lookup), and `getCredentialState` returns `.authorized` on both phones, so nothing device-side can tell their sessions apart. Tell users to use separate Apple IDs (Family Sharing keeps purchases shared).
- `AppStateManager.isAuthenticated` is a UserDefaults bool, not proof of credentials — it's gated on `TokenStore.hasTokens` in memory only. Never persist that downgrade: tokens are `kSecAttrAccessibleAfterFirstUnlock`, so a pre-first-unlock background launch reads nil on a perfectly good session. Same reason `MADWatchBridge` withholds `authToken`/`backendUserId` when `SessionIdentity.isMismatched` — the watch has no refresh, no sign-out and no auth UI, so a bad pair wedges it permanently.

## Do NOT
- Add a capability by hand-editing a `.entitlements` file (e.g. `com.apple.developer.associated-domains`) WITHOUT enabling it in Signing & Capabilities / on the App ID — the app builds and installs, then gets killed by AMFI at launch (`Thread 1: abort with payload or reason`, `__abort_with_payload`, generic reason). A successful build is not proof the entitlement is provisioned; the kill is at launch.
- Change the API base URL without coordinating both client and server.
- Modify the Xcode project file (`project.pbxproj`) — it's excluded via .claudeignore. Equally, do NOT worry about it when CREATING .swift files in the MAIN app (incl. `Widgets/`, `Shared/`): synchronized folders pick up files on disk automatically. EXCEPTION: the Watch target ("Mile A Day Watch Watch App/") is NOT synchronized (its files were pbxproj-registered) — modify existing watch files only, never create new ones from CLI. And some MAIN-APP files are ALSO members of the Watch target: a new main-app file joins the iPhone target ONLY, so giving a dual-membership file a new dependency compiles on iPhone and fails the Watch with `Cannot find '<Type>' in scope`. Put what such a file needs INSIDE it (that's why `WorkoutDedup` lives in HealthKitManager.swift and `PostedWorkoutRegistry` in CelebrationManager.swift), dependency-free — no SwiftUI/MADTheme/FitnessSourceCatalog — and let iPhone-only callers delegate to it. `#if os(watchOS)` inside a file (HealthKitManager.swift) proves membership but its ABSENCE proves nothing — CelebrationManager.swift carries no conditional and is a member anyway, so assume any Managers/ or Models/ file might be. Check one before adding a dependency to it: `xcrun swiftc -typecheck -sdk $(xcrun --sdk watchos --show-sdk-path) -target arm64_32-apple-watchos10.0 <file>` and confirm the new symbol isn't in the unresolved list (compiled alone, cross-file types resolve to nothing, so read only the name you added). CI can't catch this: `ios.yml` type-checks `app/Mile A Day/**` as one module and never builds the Watch target.

## App Store Review Compliance
Every change must pass App Review. Check BEFORE proposing and AFTER implementing. Flag any borderline item explicitly.

- **Private APIs / SPI**: no underscored AppKit/UIKit selectors, no `dlopen` of system frameworks, no swizzling Apple classes. (Guideline 2.5.1)
- **Permissions & purpose strings**: any new HealthKit/Location/Notifications/Contacts/Camera/Photos use needs a clear `NSUsageDescription` in Info.plist explaining *why*. Don't request data you don't use. (5.1.1)
- **HealthKit specifics**: don't store HK data in iCloud, don't use HK data for advertising, request only the read/share types actually used. (5.1.3)
- **Background modes & BGTask**: only declare modes the feature actually needs. No keeping the app alive for tracking.
- **Account/data deletion**: if we add account creation, in-app deletion must exist (5.1.1(v)).
- **Sign in with Apple**: required as an option if we add any third-party social login (4.8).
- **Payments**: any digital goods/subscriptions = StoreKit/IAP only. No external payment links for in-app digital content. Physical goods/services = Apple Pay or other. (3.1.1, 3.1.3)
- **Push notifications**: not for ads/marketing without explicit opt-in. Friend hype/notifications must be user-controllable. (4.5.4)
- **User-generated content / social**: competitions + friend features need reporting, blocking, and a moderation/EUA path if users can send each other content. (1.2)
- **Health & safety claims**: don't claim medical/health benefits in copy or marketing without basis. "Mile a day" framing is fine; avoid medical guarantees. (1.4.1)
- **Kids / age**: app is not in Kids Category; don't add behaviors that target under-13s.
- **Web views & external links**: avoid linking out to purchase flows; in-app browsers must be SFSafariViewController or WKWebView with clear UX.
- **Entitlements**: don't add capabilities (iCloud, Game Center, Associated Domains, etc.) without a shipping feature that uses them. Don't remove entitlements an existing feature depends on.
- **Copy & metadata**: no mentions of beta/test, no placeholder text in user-visible strings, no references to other platforms.
- **Assets**: icons/screenshots must match shipped UI; no Apple trademarks or hardware mockups in icons.
- **Privacy manifest (`PrivacyInfo.xcprivacy`)**: if we add a new SDK or new data collection, update the manifest and required-reason API declarations.

When in doubt: cite the guideline number, propose the compliant path, and ask before shipping.
