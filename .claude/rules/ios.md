# iOS App Conventions

## HealthKit
- Workout sync: HealthKit -> WorkoutProcessor -> WorkoutSyncService -> Backend API
- Every automatic upload trigger (observer, foreground, BGTask, launch) funnels through `syncNewWorkouts`'s `guard !isSyncing`: the flag must clear via `defer` — a rethrow once stranded it true, starving ALL sync for the process lifetime ("dashboard done, friends list 0.00, posts 403 until Sync Streak"). Its incremental filter scans 48h BEHIND `lastSyncDate` (uploaded-ids set dedupes, watermark is monotonic) — strict `endDate > lastSync` permanently dropped late-landing Watch workouts, same trap as WorkoutIndex.
- HealthKit queries ERROR when the device is locked (protected data). Never treat a query error as "0 miles" — only a successful empty result is a real zero. Writing 0 on error randomly reset widgets.
- Feed route maps are read from HKWorkoutRoute at sync time. In-app tracked workouts must write their GPS trace via `HKWorkoutRouteBuilder.finishRoute` after `finishWorkout` (and `HKSeriesType.workoutRoute()` must be in the SHARE auth set) — points buffered in InProgressWorkoutStore alone never reach the backend. AND the HealthKit observer fires on `finishWorkout` itself, BEFORE the route exists — that raced sync uploads route-less and marks the workout synced, so the feed map never appears while Apple Fitness (reading HealthKit directly) shows it fine. The finish must call `WorkoutSyncService.uploadWorkout(withId:)` after `finishRoute` lands — safe both ways because `workout_routes` only upserts when a payload HAS a route (fullSync/recalibrate re-pushes never erase routes).
- A route polyline drawn OVER an `MKMapSnapshotter` image must be projected with `snapshot.point(for:)` — never a linear lat/lon→pixel map of the requested `MKCoordinateRegion`. MapKit EXPANDS the region to fit the requested image aspect, so the region never describes where a coordinate landed; and the image is displayed `.aspectRatio(.fill)`, so a snapshot whose size doesn't match the view is scaled+cropped while the line isn't. `WorkoutRouteMapView` requested a fixed 400×300 for a 4:5 card and stretched every track ~1.7× horizontally — a shoreline walk drew out in the bay while Apple Fitness (same HKWorkoutRoute) was fine. Snapshot at the view's own size and pass `RouteMapSnapshot` (image + size + projection) to anything compositing it. `RunPostService.renderRouteImage` was always right; compare against it.
- WidgetKit renders statically: `.onAppear`-driven `@State` animations never play in widget views — render entry values directly (for a day-walk, bake per-hour `Timeline` entries — that spends NO reload budget). `WidgetDataStore` data is day-stamped; `load()` returns zeros for a stale day, and saves skip no-op writes (widget reloads are budgeted per day). The widget process can't read `UserDefaults.standard` — any app pref a widget needs (e.g. dashboard style for `StreakFlameWidget`) must be mirrored into the App Group via `WidgetDataStore`. New widget files go in `app/MileADayWidgets/` (a synchronized folder — auto-joins the widget target, no pbxproj); `app/Mile A Day/Widgets/` files need pbxproj membership.
- Dashboard style uses `dashboardStyleV1` / `dashboardStyleChosenV1`: Modern is the default. Both dashboard heroes share the flame lifecycle (`StreakFlamePhase` + `StreakFlameClock`): coal at streak 0, burning shrinks with time left (SIZE signals time — never fade opacity), blazing when done. Only dashboards pass `phase:`/`dayEnd:` into `FlameBuddyView` — legacy callers (chooser preview, Live Activity `FlameBuddyFigure`) stay phase/vigor-less to keep the old stage look, and static buddy code must stay copied in both widget locations when Live Activity visuals change. The goal celebrations' `ReignitingFlameView` takes a `FlameRevivalOrigin` derived from the streak — `.coal` ONLY when the flame was actually out (streak <= 1); both views hardcoded it, so a 400-day streak was told daily that it had died and been revived. NEVER animate a flame by opacity-crossfading two `FlameBuddyFigure`s: they wobble on different curves and each draws its own glow + ground shadow, so the pair ghosts apart mid-fade and reads as a second flame appearing and going away. Warm ONE figure instead — `FlameBuddyFigure(blaze:)` blends the live vigor palette/glow/core into the `.blazing` look (`FlamePalette.outer/inner(vigor:blaze:)` resamples the 3-stop live gradient to the blaze's 4 stops so nothing pops at blaze 0). Its `SadEmberBuddy` is the only face the Modern side can ever draw, so it must honour `showsFace`. Both heroes' stat lines are ONE `HeroStatColumn` (DashboardModeCards) — they drifted to different stats when forked. The flame WIDGET mirrors the hero's streak box + savers chip (`FlameStreakBox`) from `WidgetDataStore` values. A value that moves all day must not reload on every write or it spends the whole budget on itself: `save(todaySteps:)` stores EXACT but only reloads per 1000-step bucket, and it's monotonic-within-day because `todaysSteps` reads 0 on a FAILED HealthKit query (locked device). `save(longestStreak:)` never reloads at all — the `save(streak:)` beside it carries one. NEVER predict a widget's usable height — a medium widget's is far below what the 170pt frame and documented content margins imply (measured under 119pt on a Pro Max), so a third stat row sized by arithmetic vanished twice. DERIVE the layout from a `GeometryReader` height (`FlameColumnMetrics.fitting`) and never let a `ViewThatFits` candidate differ in CONTENT — a wrong prediction then silently deletes a row instead of just tightening it. To measure an existing widget from a screenshot: a centred column's height is `2 * (85 - topInsetPt)`. A child taller than the canvas (a fixed-size flame) makes the HStack taller than the canvas and corrupts any GeometryReader beside it — give it `maxHeight: .infinity` and let it overflow visually.
- NO widget may poll the clock with `.after(interval)`. Its data only moves when the app writes it (which force-reloads that kind), so the ONLY scheduled reload is `.after(MADWidgetClock.endOfDay())` — five widget kinds at 30-60min policies asked ~126 reloads/day against a ~40-70 budget, and an over-budget kind has ALL its reloads dropped, the app's included, so the widget freezes while the app is right. Clock-driven state instead comes free from `MADWidgetClock.hourlyEntryDates()` (hour-ALIGNED, so the 6 PM at-risk switch fires on time) plus a baked midnight entry so the day rolls over even if that one reload is dropped. Never bake a countdown STRING into an entry — an entry can sit on screen for an hour ("7h 24m left" vs the app's "6h 30m"); use `MADWidgetCountdown.text(to:)` (`Text(_:style:.relative)`, which the system re-renders itself).
- Background HealthKit reads must gate on `hasLoadedInitialData`, not a fixed sleep — on a locked device queries error, `retroactiveStreak` reads 0, and `updateFromHealthKit` persists it unconditionally (streak 0 stuck in widgets). `MADBackgroundService` must also use `UserManager.shared` / `HealthKitManager.shared`, never its own instances: a private `UserManager()` decodes `currentUser` once and never sees the app's later writes, so every background sync re-persisted that frozen copy (`updateFromHealthKit` assigns the streak unconditionally, `vettedHealthKitStreak` vets against the stale value) — the widget sat days behind a correct dashboard. And its `checkForMileCompletion` must NOT call `completeRun`: `updateUserWithHealthKitData` already stamped `lastCompletionDate`, so it only re-adds today's miles to lifetime `totalMiles`.
- WorkoutIndex incremental updates need the 48h lookback + record-id dedup: querying strictly from `lastUpdated` permanently drops workouts that reached HealthKit late (Watch sync), leaving a `qualifyingDays` hole — `activeStreak()` stops there and the dashboard flashes a tiny streak until the backend rescue lands. Backend-streak ≫ local triggers a debounced rebuild (`repairWorkoutIndexIfStale`).
- The displayed streak (`currentUser.streak`) is quarantine-gated: `UserManager.vettedHealthKitStreak` refuses 2+ day drops from local recomputes unless the backend (48h-fresh, recomputed server-side every `getUserStats`) agrees or a same-day full index rebuild confirms. Never write `hk.retroactiveStreak` raw to UI/widgets/watch — it flaps on index holes; route through `updateUserWithHealthKitData` / push `max(hk, user.streak)`.

## Key Patterns
- `FreshPostWindowManager` GATES posting (10 min per qualifying walk/run). Seven affordances read it and must stay in sync: the feed FAB, `StoriesRailView.canPost`, `SocialFeedView.handleCompose`, `BuddyRecapView`, `PostRunPhotoPromptView` (auto-skips to the `is_auto` card if the celebration queue outlasts the window), and the "Add to feed" promote in BOTH `StoryViewerView` and `ProfilePostsGridView`/`WorkoutDetailView` (that promote is a PATCH, not createPost — the easy one to miss). It anchors to OBSERVATION time, not `HKWorkout.endDate`, so a late Watch sync gets a full window — which also means a workout the app never saw opens no window at all; `syncPostWindow()` adopts the server's via `GET /posts/window` (adopt-only: never shortens an open window, never closes one). `isOpen` reads the wall clock, so nothing publishes at expiry on its own — that's `scheduleExpiryTick` plus `refresh()` on foreground. The "FRESH" chip is GONE (gated posting makes every post fresh); `is_fresh`/`posted_fresh` stay on the wire for pre-gate builds only.
- Backend `timestamptz` serializes WITH fractional seconds (`…:15.600Z`) and `APIClient`'s decoder uses `.iso8601`, which CANNOT parse those — one bad date fails the WHOLE payload. Type backend timestamps as `String` in DTOs and parse with `[.withInternetDateTime, .withFractionalSeconds]` (see `BuddyDate`); only `date` columns are safe as plain strings.
- Any "did they hit the mile today" SCORING check is `ProgressCalculator.isGoalCompleted(current:goal:)` (0.95 tolerance, mirrors backend `DAILY_GOAL_TOLERANCE`), NEVER a raw `>= goal` — a strict compare renders a completed-per-server day as orange/incomplete (`Last7DaysChart`, the friends hero card, `hasCompletedGoalToday` all had it). EXCEPTION: the in-workout celebration/goal-alert fires at the full goal — see the tracking bullet. Competition goals are a DIFFERENT threshold — server-scored exactly; don't sweep those into the tolerance. Clamp the goal `> 0` first: the helper is `current >= goal * 0.95`, vacuously true at goal 0.
- NEVER read `HKWorkout.totalDistance` for anything a user sees or that gets summed — use `workout.madDistanceMiles` (HealthKitManager.swift, so the Watch target sees it). It floors a walk at `TrackedWorkoutLedger`'s receipt: the exact number `liveDistance` showed when Finish was pressed, stamped in `finishWorkout`'s completion. Without it the tracked number was handed to HealthKit and thrown away, so five pipelines each re-derived the distance and any of them could come back LOWER ("0.34 while walking, 0.22 once it saved"). `HKWorkoutBuilder.add`'s error was discarded (Workouts share access granted + Walking+Running Distance denied ⇒ a workout with no distance, silently); `needsNewWorkoutFetch()` holds `cachedWorkouts` fresh for an HOUR, so the Workouts screen summed a day missing the walk that just ended (`invalidateWorkoutCacheFreshness()` before the post-save fetch); and `WorkoutDedup` could vote it out. A tracked workout now ranks above everything in `duplicateSources` and is never excluded. Sync uploads `madDistanceMiles` too, or the server disagrees with the phone.
- `WorkoutDedup.exclusions` runs duplicate detection over what the CONSENT pass left (`breakdown(in:)` — use it, not the two calls separately): handing `duplicateSources` the full array let an un-approved copy be the keeper, marking the approved one `.duplicate` while the keeper stayed `.sourcePending` — the walk left the total twice and landed in it zero times. And source consent is grandfathered by a TIMESTAMP (`isBeforeGrandfatherLine`), not just a bundle-id sweep: that sweep reads `recentWorkouts`, filled by a separate async query that answers nothing on a locked device, so a source missed in that instant silently subtracted itself from every daily total thereafter. Explicit `.ignored` still outranks the line.
- A per-day chart must take the profile OWNER's `goalMiles`, not a hardcoded 1.0 — `Last7DaysChart` painted a 2-mile-goal friend green at one mile.
- Use `@Observable` (iOS 17+ Observation framework) for new view models.
- Feature views live in `Views/<FeatureName>/` subdirectories.
- Shared UI components in `Views/Components/`.
- Watch app is a separate target at `Mile A Day Watch App/`.
- One post opens as ONE post: `PostDetailView` (list sliced to start AT the target — never scroll-to-with-an-opacity-mask) fed by the grid's binding, or `PostDetailLoaderView` for a `post_id` from a push/`mileaday.run/p/<id>` link. `MainTabView` presents it via `PostDeepLink`; from inside a sheet use `openAfterDismiss`. `FeedDeepLink` (scroll the feed) is now only for raw workouts, which have no permalink.
- A Streak Assist takes both sides, so no single button completes one: `SaveFriendStreakView` OFFERS (lands on "Mile offered", never a "Saved!" checkmark for a save that hasn't happened) and the friend accepts from `StreakAssistOfferSheet`, which is hosted at MainTabView root for the same reason celebrations are. Its CTA is gated on the caller's SPARE MILES (`donation_budget.remaining`) and the FRIEND's token — the locked state says how much further to run today, which unlike a 20-mile meter is closable this afternoon. `my_savable_day` is the only honest trigger for the ask CTA: the streak number can't tell whether one covered day would reconnect. `FriendService.friends` is EMPTY until the Friends tab has been visited, so any sheet opened from the Dashboard must load it before treating empty as "no friends".
- A view whose body renders `EmptyView` gets NO lifecycle: `.task`/`.onAppear` on it never fires. A state machine that starts in an empty phase and loads from `.task` self-deadlocks (empty → no task → still empty) — `SaveFriendStreakView`'s Save Streak CTA was invisible on every surface for this reason. Resolve the first load in the model's `init` (or from the host), and keep `.task(id:)` only for RE-loads.
- fullScreenCover gotchas (post composer): pass tap-selected content via `.fullScreenCover(item:)` (isPresented + separate @State races to a stale nil), guard onAppear side effects with a one-shot flag (onAppear RE-FIRES when a cover dismisses — an auto-opened camera re-traps the user), and attach two covers to two different nodes or one drops.
- Celebrations: `CelebrationContainerView` hosts ONCE at MainTabView root (a Dashboard-hosted overlay played invisibly whenever another tab was selected) and one-shot flags (goal-shown-today, per-workout photo prompt) stamp at DISMISSAL (`markConsumed`), never on display. `hasFreshTodaysDistance` must flip in the SAME main.async block that publishes todaysDistance/todaysWorkouts — a separate earlier dispatch let celebration checks read stale values and eat the flame/photo prompt/fresh window. The fresh window/photo prompt/composer must all share `RunPostService.dailyMileWorkoutId()`; extra-mile prompts use the newest finished workout. Mixing ids causes prompt dedup/upsert bugs.
- In-app tracking: GPS distance/route accrual must keep its noise gates (doppler-stationary skip, steps-corroboration for dopplerless fixes, dual-endpoint jitter floor, 12 m/s teleport cap, stale-fix rejection). Multipath (stadiums, urban canyons) emits `speed == -1` fixes whose SLOW drift beats any per-fix cap — sub-floor fixes hold the anchor, so displacement crosses the floor at an implied 1-2 m/s (a 3h ballgame banked 2.28 seated "miles") — so dopplerless movement only counts while CMPedometer steps advanced in the last 60s (`stepsCorroborateMovement`, fail-OPEN without Motion permission). `liveDistance` is THE workout number — every surface shows it (tracker screen/ring, celebrations, Live Activity, banner, recovery store) and Finish saves it VERBATIM; there is no finish-time re-arbitration (raw-GPS-live once read "100%" and then Finish reconciled down to 80%). TWO instruments, ONE number: `liveDistance` ratchets over `max(gated-GPS span, calibrated-pedometer span)` — deliberately LENIENT (product rule: never undercount a goal; a mis-calibrated stride loses 10-40% and a pedometer-primary handoff at 1.5× never triggers on it, which is a structural undercount; slight GPS-side overcount vs Apple Fitness is the accepted cost). Never reintroduce an instrument-picker/handoff — the max IS the design. Ratcheted monotonic: a walked mile never ticks backwards, so celebrations are final. The tracker CELEBRATES at the FULL goal (raw `>=`, product rule — 0.95 is the server's never-break-a-streak safety net, not the finish line; do NOT "fix" the celebration to the tolerance). Miles DISPLAYS floor to 2 decimals (`Double.milesText`/`milesFloor2`; widget files carry a private `flooredMilesText` copy — widget targets can't see Extensions.swift and CI compiles one module, so no shared symbol) — `%.2f` rounded 0.995 to "1.00" beside a 99% ring and no celebration. Remaining-to-goal displays CEIL (recap `milesRemaining`, dashboard "To go") — never promise the goal is closer than it is. The absurd-overcount GPS shapes (seated drift, driving) must die at ACCRUAL (doppler-stationary skip, steps corroboration, teleport cap, automotive suspension) — never re-add a downward take-back to compensate. `outdoorPedometerMiles` stays nil until CoreMotion delivers and is clamped monotonic. CMMotionActivityManager's confident-automotive verdict suspends accrual+route entirely (city driving ≈11 m/s slips UNDER the 12 m/s cap with valid doppler). `movingSeconds` (workout metadata `MAD_moving_seconds` → sync `movingSeconds` → `workouts.moving_seconds`) is the DISPLAY-pace divisor only — `total_duration` stays elapsed for PRs/races/recaps. Routes pass through `WorkoutRouteCleanup` once at finish (despike/smooth/simplify). `CMPedometer.startUpdates` and `CMMotionActivityManager.startActivityUpdates` are SUSPENDED once the phone locks (CoreMotion batches them until foreground) — i.e. for the whole of a real walk. Never treat a silent stream as a measurement: poll `queryPedometerData`/`queryActivityStarting` (`pollMotionWitnesses`, 10s) instead, and distinguish "CoreMotion answered" (`lastPedometerSampleAt`) from "the walker stepped" (`lastPedometerProgressAt`) — conflating them froze indoor distance, made `stepsCorroborateMovement` fail CLOSED (killing dopplerless accrual + route for the session), and latched a stale automotive verdict that suppressed everything. Auto-pause keys on stale movement EVIDENCE (counted segment / moving-doppler fix / **fix-to-fix displacement over ~10s from a separate `evidenceAnchor`** / step progress, 120s) — never on accrual alone (an out-and-back turnaround holds the accrual anchor while displacement round-trips under the noise floor, which flashed AUTO-PAUSED mid-stride at 0.99 mi) and never while BLIND (no usable fix ⇒ silence about movement, not evidence of stillness). Evidence uses a looser accuracy bar (120m) than accrual (50m); the chip is cosmetic, so always err toward not-paused.
- Feed/post stats linked to a `workoutId` come from that exact `HKWorkout`, EXCEPT the day's `dailyMileWorkoutId()` anchor, which bakes the rollup of every workout ending at/before it (`RunPostService.dayRollupStats`) — that's what the server restates the card with, so the leg's own number read "0.33 mi" under a "1.06 mi" headline. Extra-mile posts stay exact or they'd swallow earlier walks. The server's `auto_post_stats_mismatch` guard accepts either value. Never bake `currentUser.streak` into a post — it lags a real break by design; use `UserManager.freshBackendStreak` (the server also restamps `stats_snapshot.streak` at create).
- `center.setNotificationCategories(...)` REPLACES the whole set — pass every category (`FRIEND_ACTIVITY` + `FRIEND_REQUEST`), or an omitted one's action buttons silently vanish. Notification-action handlers run while the app may be suspended: never reach for a view-owned `@Published` service (MainTabView's `FriendService` may not exist) — build a throwaway instance or use a static path.
- A toast rendered by the PRESENTING view is invisible while its `.sheet` is up. Feedback for an action invoked from inside a sheet must be rendered by the sheet (see `FriendRequestsSheet`). Related: `FriendsListView` only exists once the Friends tab has been visited, so a `NotificationCenter` post aimed at it is dropped on cold launch — park intent on `DeepLinkRouter` and consume in BOTH `.task` and `.onReceive`.
- A badge driven only by `.onChange(of:count)` never clears a stale value: if the count starts at 0 and stays 0, the hook never fires. Pair it with an explicit set after the launch/foreground refresh.
- iOS 26 auto-wraps custom `ToolbarItem` views in a shared glass capsule. For a custom-styled pill, apply `.sharedBackgroundVisibility(.hidden)` to the `ToolbarItem` itself (it's on `CustomizableToolbarContent`, NOT a `View` modifier; gate with `#available(iOS 26)`) or it renders pill-inside-a-pill. Also `.fixedSize()` toolbar HStacks — leading items truncate `Text` to zero width otherwise.
- `.offset` draws OUTSIDE layout bounds, so a stack whose look depends on it measures wrong and everything beside it centers off: the collab header's overlapping avatars occupied 44pt while measuring 40, floating the FRESH chip 2pt high. Build overlaps with `.padding` on the underlying view + a ZStack alignment instead. A collab post also carries two names where a solo one has one — chips sharing that row need `.fixedSize()` or they compress before the names do, BUT `.fixedSize` publishes a minimum width no ancestor can shrink, so it must never wrap a label whose text is DATA: `WorkoutSourceChip`'s app name falls back to a bundle-id leaf, and "Google Health (Fitbit)" + "Not counted" needed ~241pt of a ~208pt slot, so the row → card → padded VStack demanded 487pt on a 430pt screen. A ScrollView CENTRES content it can't fit and clips both ends, so the symptom is the SCREEN GUTTER vanishing — cards flush to the bezel on a view whose padding is provably correct, and raising the gutter changes nothing because the overflow grows to match. Diagnose by measuring, not reading: a screenshot's day-grid column pitch pins the real content width (`(screen - 7c - 6·spacing)/2` = actual inset). Fix at the atom — `ViewThatFits { HStack; VStack(truncating) }`, candidates differing in ARRANGEMENT only. `is_self` is the server's "you POSTED this", so it's false for an accepted coauthor: gate hype/report/block on an is-this-mine check that also counts `coauthor_user_id == currentUserId` (`PostCardView.isMine`), or a coauthor gets a Hype button on their own post that the server then 400s.
- There is no iOS CI, so type-check edited Swift from the CLI before handing it back: `xcrun swiftc -typecheck -sdk $(xcrun --sdk iphoneos --show-sdk-path) -target arm64-apple-ios17.0 <file + its target siblings>`. `-parse` is NOT a substitute — it only checks syntax and happily accepts a nonexistent overload (`.frame(maxWidth:height:)` and `.frame(width:maxHeight:)` both shipped that way; `frame` never mixes width/height with min/ideal/max).
- A struct with an explicit `CodingKeys` enum (e.g. `FeedEntry`, which maps `entryId` ← "id") loses Codable synthesis the moment a stored property is added without a matching case or default — and with no iOS CI, the first compiler to notice is Xcode Cloud's Archive on `main` (build 413). When adding fields to a Codable struct, check for an explicit CodingKeys enum FIRST. Sibling trap for PERSISTED Codable models (`User` → UserDefaults blob, `NotificationPreferences`): synthesized `Decodable` IGNORES property defaults, so a new stored field must be `Optional` (or use `shareRouteMapsRaw`-style optional backing + computed accessor) — a non-optional addition throws on every existing install's saved blob (reads as sign-out / prefs reset).
- Deployment target is iOS 17.0. SF Symbols added after SF Symbols 5 (e.g. `figure.run.treadmill`, v6/iOS 18) render as a BLANK box on iOS 17, not a fallback. For a symbol name that may be too new, resolve it at runtime (`UIImage(systemName:) != nil ? new : oldFallback`) instead of hardcoding — a build with a newer SDK won't catch it.
- Link to a third-party app ONLY by App Store id — `itms-apps://apps.apple.com/app/id<N>`, https as backstop (`FitnessSourceLauncher.openAppStore`). Custom URL schemes are first-come-first-served and unverifiable, so a guessed one does NOT fail, it opens whichever other app claimed it: `fitbit://` opened an unrelated fitness app from the Google Health row. Nothing in-app can detect that (`canOpenURL` needs `LSApplicationQueriesSchemes` in an Info.plist GENERATED from the off-limits `project.pbxproj`, so it just returns false), which is why there is no safe way to keep one. A product page resolves to exactly one app and already shows OPEN when it's installed, so the shortcut bought almost nothing. Do NOT "fix" this back to an `apps.apple.com/search?term=` url either — no storefront segment, resolves nowhere, and that dead end is what made every button look broken.
- History import (`WorkoutArchiveParser` → `WorkoutImportService`) writes backdated `HKWorkout`s rather than uploading straight to the backend, and that is load-bearing: the local streak comes from HealthKit (`WorkoutIndex`/`retroactiveStreak`) and `vettedHealthKitStreak` quarantines backend-vs-local disagreement, so server-only history would sit permanently in the repair state. Two traps in the formats: Strava's `activities.csv` repeats `Distance`/`Elapsed Time` (summary block follows the athlete's unit preference, the LATER block is raw metres/seconds — take the last), and its `Activity Date` is UTC with no offset marker, so parsing it device-local shifts evening runs a day and invents/breaks streaks — pin the DateFormatter to UTC + `en_US_POSIX`. km vs miles is NOT inferable from the file, hence the mandatory preview with a unit override. Imports carry MAD's OWN bundle id, so server dedup (different-app only) can never catch a double import — `ImportedWorkoutRegistry` plus the `MAD_import_key` metadata probe is the only guard. Never stamp `HKMetadataKeyWasUserEntered`: that reclassifies the workout as manual.

- Periodic work during tracking (watchdog re-arm, presence heartbeats) must ride the location/pedometer CALLBACKS, not view timers — the view's 1s Timer suspends while the app is backgrounded even though the `location` background mode keeps delegate callbacks firing (`LivePresenceService.tick()` self-throttles, so callers call it freely from both). And in-workout feedback (hype toasts) must render INSIDE WorkoutTrackingView — it's a fullScreenCover, which sits on top of MainTabView's global `InAppBannerManager` overlay.
- Tracking liveness has three layers — keep all three when touching the tracker: (1) `armTrackingWatchdog` slides a 5-min dead-man local notification forward from location AND pedometer callbacks (it fires only if iOS terminates the app mid-workout; when-in-use permission can't relaunch, so termination is otherwise silent); (2) the Live Activity renders `context.isStale` as TRACKING INTERRUPTED — every pushed content INCLUDING the initial `Activity.request` must carry a `staleDate` or the flip never happens, and the self-ticking `Text(timerInterval:)` otherwise keeps counting on a dead workout; (3) the tracking screen banners denied/reduced-accuracy/no-fix states — Precise Location OFF means every fix fails the <50m accuracy gate and the workout reads 0.00 forever while looking alive. Background App Refresh and Low Power Mode do NOT kill an active `location`-background-mode session by themselves; LPM only raises the odds of (1).

## Auth / Session
- "Who am I?" is the access token's `sub` (`TokenUtils.subject`), never a cached id. Self-scoped URLs are built from `UserManager.currentUser.backendUserId` / `UserDefaults["backendUserId"]`; when those drift from `sub` the server answers **403**, and `APIClient` only recovers on 401 — the app stays "logged in" with friends + daily challenges dead forever. `SessionIdentity.enforce()` (launch, foreground, and on 403) is the only thing that catches it. Never blanket-sign-out on 403: it's also "not friends"/"admin only".
- Two people on ONE Apple account cannot have two MAD accounts — `/auth/signin` resolves the user by EMAIL alone (`apple_sub` is written at creation, never used for lookup), and `getCredentialState` returns `.authorized` on both phones, so nothing device-side can tell their sessions apart. Tell users to use separate Apple IDs (Family Sharing keeps purchases shared).
- `AppStateManager.isAuthenticated` is a UserDefaults bool, not proof of credentials — it's gated on `TokenStore.hasTokens` in memory only. Never persist that downgrade: tokens are `kSecAttrAccessibleAfterFirstUnlock`, so a pre-first-unlock background launch reads nil on a perfectly good session. Same reason `MADWatchBridge` withholds `authToken`/`backendUserId` when `SessionIdentity.isMismatched` — the watch has no refresh, no sign-out and no auth UI, so a bad pair wedges it permanently.

## Do NOT
- Add a capability by hand-editing a `.entitlements` file (e.g. `com.apple.developer.associated-domains`) WITHOUT enabling it in Signing & Capabilities / on the App ID — the app builds and installs, then gets killed by AMFI at launch (`Thread 1: abort with payload or reason`, `__abort_with_payload`, generic reason). A successful build is not proof the entitlement is provisioned; the kill is at launch.
- Change the API base URL without coordinating both client and server.
- Modify the Xcode project file (`project.pbxproj`) — it's excluded via .claudeignore. Equally, do NOT worry about it when CREATING .swift files in the MAIN app (incl. `Widgets/`, `Shared/`): synchronized folders pick up files on disk automatically. EXCEPTION: the Watch target ("Mile A Day Watch Watch App/") is NOT synchronized (its files were pbxproj-registered) — modify existing watch files only, never create new ones from CLI. And some MAIN-APP files are ALSO members of the Watch target (`HealthKitManager.swift` — the tell is `#if os(watchOS)` inside it): a new main-app file joins the iPhone target ONLY, so giving a dual-membership file a new dependency compiles on iPhone and fails the Watch with `Cannot find '<Type>' in scope`. Put what such a file needs INSIDE it (that's why `WorkoutDedup` lives in HealthKitManager.swift), dependency-free — no SwiftUI/MADTheme/FitnessSourceCatalog — and let iPhone-only callers delegate to it. CI can't catch this: `ios.yml` type-checks `app/Mile A Day/**` as one module and never builds the Watch target.

## App Store Review Compliance
Every change must pass App Review. Check BEFORE proposing and AFTER implementing. Flag any borderline item explicitly.

- **Private APIs / SPI**: no underscored AppKit/UIKit selectors, no `dlopen` of system frameworks, no swizzling Apple classes. (Guideline 2.5.1)
- **Permissions & purpose strings**: any new HealthKit/Location/Notifications/Contacts/Camera/Photos use needs a clear `NSUsageDescription` in Info.plist explaining *why*. Don't request data you don't use. (5.1.1)
- **HealthKit specifics**: don't store HK data in iCloud, don't use HK data for advertising, request only the read/share types actually used. (5.1.3)
- **Background modes & BGTask**: only declare modes the feature actually needs. No keeping the app alive for tracking.
- **Account/data deletion**: if we add account creation, in-app deletion must exist (5.1.1(v)).
- **Sign in with Apple**: required as an option if we add any third-party social login (4.8).
- **Payments**: any digital goods/subscriptions = StoreKit/IAP only. No external payment links for in-app digital content. Physical goods/services = Apple Pay or other. (3.1.1, 3.1.3)
- **Push notifications**: not for ads/marketing without explicit opt-in. Friend hype/notifications must be user-controllable. (4.5.4)
- **User-generated content / social**: competitions + friend features need reporting, blocking, and a moderation/EUA path if users can send each other content. (1.2)
- **Health & safety claims**: don't claim medical/health benefits in copy or marketing without basis. "Mile a day" framing is fine; avoid medical guarantees. (1.4.1)
- **Kids / age**: app is not in Kids Category; don't add behaviors that target under-13s.
- **Web views & external links**: avoid linking out to purchase flows; in-app browsers must be SFSafariViewController or WKWebView with clear UX.
- **Entitlements**: don't add capabilities (iCloud, Game Center, Associated Domains, etc.) without a shipping feature that uses them. Don't remove entitlements an existing feature depends on.
- **Copy & metadata**: no mentions of beta/test, no placeholder text in user-visible strings, no references to other platforms.
- **Assets**: icons/screenshots must match shipped UI; no Apple trademarks or hardware mockups in icons.
- **Privacy manifest (`PrivacyInfo.xcprivacy`)**: if we add a new SDK or new data collection, update the manifest and required-reason API declarations.

When in doubt: cite the guideline number, propose the compliant path, and ask before shipping.
