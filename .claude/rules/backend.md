# Backend Conventions
- Feed reads must stay bounded by the PAGE and the viewer's CIRCLE. Two ways they silently stop being: (1) a candidate arm with no per-owner `ORDER BY … LIMIT` reads the circle's whole history / every shared post in the DB and sorts the lot — `UNIFIED_FEED_SQL`'s arms are a LATERAL per circle member for exactly this reason (a row in the global top-N is necessarily in its owner's top-N), and the cursor is pushed INTO each arm or page 2 costs what page 1 costs; (2) a predicate that doesn't state what a PARTIAL index is partial on. Every hype index leading with `target_id` is `WHERE context_id IS NOT NULL`, and Postgres can't prove that from a pile of ORed equality tests — so it discarded them and read ALL of hype_log per feed card (63ms of a 99ms query). `CONTEXTFUL` in hypeService states it; keep it on any new hype predicate. Also: the pool sets `jit = off` (DbService) — LLVM codegen engages purely on estimated cost crossing a threshold, so it switches itself on as tables grow and adds ~200ms to a query whose plan nodes account for 35ms. The tell is `unaccounted_ms` in `/status/schema?profile=feed`. Verify feed-query changes by DIFFING old vs new output over seeded collabs/blocks/private authors, never by reading them.
- Photo posting has TWO tiers, both from `getPostWindowStatus` (postService): `cameraOpen` = 10 min from a qualifying workout, and `photoOpen` = a qualifying workout exists for that local day. Qualifying = `feed_role IN ('daily_mile','extra')`, so never re-derive that set by hand. Which tier applies is the client's declared `photo_source` (`photoSourceRequiresCameraWindow`): only a LIVE capture is on the clock; a camera-roll pick or a promoted story is bounded by when the photo was SHOT, which the importer already enforces client-side, so charging it the countdown only punishes finishing your cooldown. Absent/unknown source ⇒ camera tier, i.e. exactly what pre-split builds ship against. Anchored to `GREATEST(device_end_date, created_at)`: `created_at` is absent from the sync upsert's `DO UPDATE`, so a fullSync can't reopen a closed window, and a late Watch sync still gets its full 10 min. TWO paths put a photo on the feed and both must gate — `POST /posts` AND `PATCH /posts/:id {add_to_feed:true}` (promoting a story is the same user action, and was the whole bypass); the PATCH is `photoOpen`, since that photo was captured under whatever rule applied then. `is_auto` posts are exempt (the skip-the-prompt route card). Gated per device on `CLIENT_FEATURES.postWindowV1`. The 403 string stays `post_window_closed` (shipped builds match on it); `reason`/`photo_open` are the additive half. `posted_fresh`/`is_fresh` survive as write-and-serve only — current builds dropped the FRESH chip but pre-gate builds still send and render it, so never remove the column or the response field. The window also HOLDS the raw workout card off other viewers' unified feeds (10-min CAMERA tier, same GREATEST anchor, workout arm of `UNIFIED_FEED_SQL`; owner exempt) and ALL three friend workout pushes defer to its close (`pending_friend_notifications.send_after_at`) — post + route land together, and a push can never point at a held card. Those two timings move with the camera window or a push taps to nothing; ci-smoke seeds must age `created_at` past it before asserting a friend sees a workout card.
- Daily-mile completion checks must use `DAILY_GOAL_TOLERANCE` (0.95) from workoutService, never a raw `>= 1.0` — streaks/challenges count 0.95 days, and today_miles is displayed 2-decimal-rounded ("1.00" can be 0.996). iOS mirror: `ProgressCalculator.dailyGoalTolerance` / `isGoalCompleted(current:goal:)` — and that helper is `current >= goal * 0.95`, so a goal of 0 makes it vacuously TRUE; clamp the goal before calling it. `user_daily_challenges` stamps which challenge a user was SERVED on a date (first-write-wins, from their own dashboard read and the sync-time evaluation — never the friend-profile read, which resolves someone else's day); missed-day history reads stamp → `h2h_matchups` → re-derivation, because re-deriving a past date silently changes answer whenever the rotation does. Challenge queries that reach workouts through `workout_splits` must ALSO carry `countedWorkoutSql('w')`: every `SUM(distance)` one always filtered, the split-pace ones (speed_round, beat_your_pace, the `{avg_pace}` template, and the completion-detail re-derivations) did not — so a Strava duplicate or a `vehicle_speed` drive that was kept out of the user's miles still owned the fastest split, won Speed Round, and raised beat_your_pace's all-time `prior` permanently.
- A buddy walk's post carries the whole crew: `post_coauthors.media_url` is that participant's own slide (`PUT /posts/:id/crew-photo`, gated exactly like createPost — media ownership, on-disk, and the same `photoSourceRequiresCameraWindow` tier split; re-sending REPLACES), and `coauthors[].route` resolves at READ time through `buddy_session_participants.workout_id`. Resolve, never store: the reconciler stamps that id a minute or two after the walk, i.e. AFTER whoever posts on finishing has already posted, so a stored route/workout id would be permanently null for most of the crew. Each route honours THAT person's `share_route_maps`, never the poster's, and the poster's per-post `include_route` still covers the whole card. `lockUnearnedPhotos` must blank `coauthors[].media_url` too (viewer's own slide exempt) or the earn-to-view gate hands over three unearned photos on the one card it exists for. `posts.buddy_session_id` answers "is this walk already posted" for EVERY participant — `post_coauthors` has no row for the author, so a solo-crew post was unfindable by session. Verify with `scripts/buddy-group-post-check.mjs`; every failure here is silent.
- `buddy_session_participants.status` is the whole membership model and three unrelated-looking reads key on the SAME set: every roster surface draws `IN ('active','finished')`, `toState`'s pooled `group_distance_miles` sums that set, and `recordProgress` 400s anything that isn't `'active'`. So a join landing the wrong enum is invisible AND worth zero AND unable to report a metre, silently — which is what `joinSession` shipped for anyone joining an already-`active` session ('joined' was only ever promoted by `activateSession`, which runs once, at start). A join into a running session must land `'active'`, and its `ON CONFLICT` guard must lift `'joined'/'ready'` too (an accepted invite sits there) while never touching `'finished'` (terminal — re-entry hands out a second mile) or `'active'`. `'left'` frees the slot and re-joins fine. Joinability windows live in TWO queries — `getJoinableFriendSessions` and the buddy decoration in `liveTrackingService.friendsOutNow` — and they must stay identical, or the Friends-tab Join button draws for an offer its own endpoint rejects. Cancel is bounded to `status='lobby' OR (status='active' AND started_at > NOW())` in the UPDATE's own WHERE, and releases people as `'left'`, never `'finished'`: `'finished'` is what the history reads, and a walk nobody took must not enter anyone's archive.
- Gaps-and-islands over dates: the island key must move OPPOSITE to the row numbering — `ORDER BY d DESC` pairs with `d + rn`, `ORDER BY d ASC` with `d - rn`. `streakEndingAt` shipped `d - rn` under a DESC walk, so the key drifted 2 days per row, every date became its own island, and it returned 1 for ANY real streak. Silent: nothing 500s, the number is just always 1 — Save Streak advertised "back to 2 days" for a 6-day run, and `recordBreak`'s `prior >= MIN_NOTIFY_PRIOR_STREAK` gate never opened so the assist-opportunity push never fired. Verify island queries against seeded dates, not by reading them.
- `streak_events.prior_streak` is a stamp-time SNAPSHOT written once (`ON CONFLICT DO NOTHING`), so fixing the code that computes it does NOT fix rows already written. Anything user-facing re-derives it at read (`stampedBreakDetail`) instead of trusting the column — that self-heals live rows with no backfill migration.
- `workouts.feed_role` ('hidden'/'rolled_up'/'daily_mile'/'extra') decides what the FEED shows, NEVER what counts — a sub-floor walk still adds to miles/streaks (that's `exclusion_reason`'s job). It must never appear in a `SUM(distance)`. Written only by `feedRoleStatements` (workoutService), which reclassifies a whole `(user, local_date)` inside the caller's transaction behind `pg_advisory_xact_lock(user)` — two devices syncing at once otherwise each pick an anchor and the mile shows twice. Recompute after ANY workout mutation, including the workout's OLD local_date on re-upload (the upsert sets `local_date = EXCLUDED`). Feed/friend-activity/profile-grid all restate a `daily_mile` anchor with the day's rollup; if you add a surface that reports a run's distance, restate it there too or the same run reads two numbers.
- Cross-app duplicates: every third-party platform (Strava, Garmin, WHOOP, Peloton…) reaches us through HealthKit, so the SAME run arrives twice with two UUIDs and UUID dedup can't see it — `duplicateExclusionStatements` (workoutService) pairs them on different `source_bundle_id` + ≥50% time overlap + ~20% distance agreement, and MUST be spliced AFTER the upsert (which resets `exclusion_reason` to the speed classification, wiping any mark) and BEFORE `feedRoleStatements` (which hides anything excluded). It only ever writes `exclusion_reason` where it IS NULL and only clears its own `'duplicate_source'`, so a `vehicle_speed` exclusion is never clobbered. Exclusion is gated on `created_at >= users.dedupe_since` — that column's `DEFAULT now()` deliberately stamps every pre-existing row with the deploy instant (the usual missing-value gotcha, used ON PURPOSE as a grandfather line) so no historical total moves; only `POST /workouts/:id/duplicates/resolve` moves it back. Kill switch `WORKOUT_DEDUPE`, default off; detection still fills `duplicate_of`.
- A Streak Assist costs TWO people two things and neither can spend it alone: the RECIPIENT's held token pays for the `streak_coverage` row, the DONOR pays one mile run past their own goal that day (N friends in a day = N miles past goal). The token itself is TIME, not effort: one per 30 days measured from `streak_assist_last_used`, so it needs no query (`assistDaysElapsed`) and a NULL reads as held — a new account holds its first, which is deliberate (the alternative is the feature not existing for a user's first month). So it is an exchange with a pending state (`streak_assist_offers`, `initiator` = who must be answered), and coverage only ever appears on an accept. The donor's mile is committed at OFFER time — checked again at ACCEPT against the offer's own `donor_date`, not today, because the row is already inside `used` and a workout can shrink after the offer. Nothing expires these rows: an offer is exactly as alive as its target day, which every read re-derives (`validateTarget`). A savable day is a MISS *or* today-not-yet-run (`pickTargetDay`, the one place those three shapes live — the batched friends list and the per-user read both call it). Availability must NOT hide behind the recipient's own Double Down / Streak Save: the sweep returns "waiting" on an open DD window, which hid the CTA for a whole day while the streak read broken everywhere — report it as `self_recovery` and let the confirmation say so. Anything advertising an exchange must re-run the gap check (`stampedBreakDetail().bridged`) or the CTA promises a save the POST 409s, and must scope "already offered" to the target date IN PLAY or yesterday's accepted row masks today's need. `prior_streak` is the run that ENDED at the miss — the number to show a user is `restored_streak`.
- Streak tokens (streak_coverage): any code that recomputes a streak MUST branch through `coverageActiveFor`/`computeCoveredStreak` (streakFeatureCore) like getActiveStreak + refreshCurrentStreak do — the 6h `reconcileStaleStreaks` cron rewrites `current_streak` via refreshCurrentStreak, so an unrouted walk silently erases token-saved streaks. Un-enrolled/env-off users must keep the byte-identical legacy loop. Meters are DERIVED from workouts since `*_last_used` (never stored counters). Raw-SQL `timestamptz` columns come back as JS Date objects (only `date` cols are strings) — `to_char(...)` in SQL or coerce before any string op; a `.slice()` on `streak_features_at` 500'd the status endpoint in prod.

## Architecture: Routes -> Controllers -> Services
- `routes/` - Express Router definitions. Thin: just wire HTTP verbs to controller functions + middleware.
- `controllers/` - Request/response handling. Parse params/body, call services, format responses.
- `services/` - Business logic and DB queries. No Express types (Request/Response) here.
- `types/` - TypeScript interfaces for domain objects.
- `cron/` - Scheduled jobs (competitions, notifications).

## Database
- `PostgresService` is a singleton wrapping `pg.Pool`. Get it via `PostgresService.getInstance()`.
- Raw SQL (parameterized `$1, $2, ...`) AND Drizzle ORM coexist on the SAME pool. Existing code is raw SQL; new code may use the ORM.
- Connection string from `DATABASE_URL` env var.
- Services instantiate `PostgresService.getInstance()` at module top-level. `server.ts` MUST `import 'dotenv/config'` as its first line — if dotenv loads after the route imports, the Pool gets `connectionString: undefined` and falls back to OS user (error: `no pg_hba.conf entry for host ..., user "<osuser>", database "<osuser>"`).

## Drizzle ORM + Migrations
- Schema-as-code lives in `src/db/drizzle/schema.ts` (generated by `drizzle-kit pull`; it is the source of truth). Config: `drizzle.config.ts`.
- New typed queries: `import { db, schema } from './DbService.js'` then `db.select().from(schema.users)`. ORM returns **camelCase** keys (`userId`); raw SQL returns **snake_case** (`user_id`) — don't swap one for the other in a function whose callers depend on the existing key casing.
- Date/timestamp columns use `mode: 'string'` to match the raw-SQL OID-1082 string behavior. Keep it that way.
- Schema change workflow: edit `schema.ts` → `npm run db:generate` (writes `NNNN_*.sql` + snapshot) → review SQL. NEVER hand-edit an applied migration. Pending migrations auto-apply at server BOOT (`src/db/runMigrations.ts`) — deploys are git-driven with no shell access; there is no manual `db:migrate` step in prod.
- If two branches both add migrations, a merge silently corrupts `meta/_journal.json` (one side's entries vanish while its .sql files remain). Resolve by REGENERATING: restore one side's journal+snapshots, delete the other side's .sql, and `db:generate` its DDL back as the next index. `npx drizzle-kit check` must pass.
- Existing prod schema was baselined via `scripts/drizzle-baseline.mjs` (records `0000` as applied without running it). Run it ONCE per environment before the first `db:migrate`.
- `drizzle-kit pull` has introspection bugs to fix by hand after every pull: (1) some SQL-expression/empty-string defaults emit broken TS → fix with `.default(sql\`...\`)` / `.default('')`; (2) composite-index per-column opclasses get misaligned (text col tagged `timestamptz_ops` etc.) → these are all DEFAULT opclasses, so strip every `.op(...)` EXCEPT non-defaults like `gin_trgm_ops`; (3) `relations.ts` imports `./schema` without `.js` → add it. After fixing, regenerate the baseline (empty `meta/_journal.json` + `db:generate`) and confirm it says "No schema changes".
- Never emit raw `timestamptz::text` in URL query params (pagination cursors): its `+00` offset decodes as a SPACE in Express's query parser and the `::timestamptz` cast 500s. Emit cursors via `URL_SAFE_CURSOR` (ISO `…Z`, postService.ts); iOS must percent-encode query values with a set that excludes `+` (`PostService.queryValueAllowed`).

## Auth Pattern
- Public routes (`/auth/*`, `/dev/*`, `/status`) are mounted BEFORE `authenticateToken` middleware in server.ts. `/dev/*` endpoints are fail-closed: 403 unless `NODE_ENV=development` (`npm run dev` sets it; testing them via plain `tsx watch` won't work without it).
- Protected routes are mounted AFTER. `req.userId` is set by auth middleware (see `AuthenticatedRequest` type).
- Use `requireSelfAccess('paramName')` middleware when a route should only allow users to access their own resources.

## Adding a New Endpoint
Service (`services/`) → controller (`controllers/`) → route (`routes/`) → if a new route file, register in `server.ts` (before/after `authenticateToken` per auth needs).

## Daily Challenges
- `head_to_head` is scored END-OF-DAY by `h2hChallengeCron` (after BOTH users' local midnight + 6h late-sync grace), never at workout sync — `evaluatePredicate` returns false for it and live progress caps at 0.99. Winner push (`challenge_won`) is deferred to the winner's local 9 AM–10 PM. It appears TWICE per rotation via `rotationSequence` (a VIRTUAL duplicate inside the one walk both selection and matchmaker share — never a second catalog row: shipped builds route pushes/completions on the exact `head_to_head` string). Rivals from a user's last TWO duel days are penalty-RANKED behind fresh candidates (`recentRivalPenalty`, mirrored in `getOrAssignRival`'s late fallback) — a penalty, never a filter, so a one-friend user still duels.
- Live H2H standings pushes (`notifyH2hLeadChanges`, workout-sync path) reuse the `lead_change` type with `challenge_key: 'head_to_head'` — every shipped build routes it, a new type would tap to nothing. Debounced on `h2h_matchups.lead_notified_state`; only "you got passed" and a genuine retake push (being first to run is not taking the lead). `opponent.challengers` (others who pinned YOU today) is display-only — `resolveOne` reads the pinned rival and nothing else.
- Rivals are PINNED per day in `h2h_matchups` (reciprocal `mutual` pairs where the friend graph + each side's `h2h_close_friends_only` pref allow; one-sided fallbacks prefer 7-day-active friends; a restricted user with no close friends skips h2h in rotation). FRIENDLESS users get the `add_friend` substitute instead (catalog row with active=FALSE, awarded at friendship-accept via `evaluateAddFriendCompletion` — the sync path can't catch it). Selection parity between per-user reads and the matchmaker lives in `challengeRotation.ts` + `hasH2hRivalCandidates` — never fork that walk.

## Competition Resolution
- Team comps (`competitions.teams` jsonb + `competition_users.team_id`): team scores are DERIVED (attachTeamScores at read; never stored). ANY code deciding winners/placements/early-resolution must route through `teamAwareOutcome` — only teams win, `winner` stays a user id (winning team's best member), members share the team's placement. Forgetting it silently reverts to individual winners.
- Standings are recomputed LIVE on every read (`getUserScores` in `getCompetition`) — even for finished comps. So a competition's stored `end_date` directly bounds which days count (scoring includes `local_date <= end_date`; `local_date` = workout START date in user tz).
- When resolving EARLY (target/goal/duration hit, not a preset end_date), set `end_date` to the last COMPLETED interval (`lastCompletedIntervalEnd`), NOT the resolution day. Resolution scoring excludes the current interval, so stamping `end_date = todayStr` makes the live recompute fold that day back in once the calendar advances → phantom points/placement drift.

## Hypes & Posts
- 'mile' hypes key on `<userId>:<localDate>` composites only (`canonicalizeMileContext` at send; migration 0012 collapsed legacy workout_id rows). Match via `mileHypeKeyMatchSql` — never hand-write the encoding.
- `express.json` limit is 2mb because workout-sync bodies carry GPS routes. Don't shrink it.
- `posts.is_auto` is tri-state at the API (`is_auto` absent = legacy client → upsert-in-place + auto-signature heuristic). A flagged user post may only replace an auto post; second user post → 409 `workout_already_posted`.
- `/uploads/posts` requires signed urls (`mediaSigningService`). Any endpoint RETURNING `media_url`/`story_photo_url` must wrap the payload in `signMediaUrlsDeep(...)`; any endpoint ACCEPTING a media_url must `stripMediaQuery(...)` first. The DB stores bare paths only.
- Direct post access (comments/mentions/coauthor respond) authorizes via `visiblePostAuthor`/`visiblePostAuthors` (postService). It must mirror the feed queries' circle+block rules — including accepted-coauthor reach and blocks vs EITHER author. Any NEW surface that shows someone else's photo (e.g. buddy history's `buddySessionPhotos`) belongs in postService behind `DIRECT_POST_ACCESS_SQL` too, and stays subject to `lockUnearnedPhotos`: "we were on that walk together" is not permission — the photo can have been made private, un-shared or blocked since, and a visibility rule re-derived from the OTHER feature's roster is a leak nobody will notice.
- A collab post has TWO owners, so nothing about it may be gated on friendship with `posts.user_id` alone — that 403'd hypes from the coauthor's friends after the client had played the animation. Post-context hypes/hyper-lists authorize on `visiblePostAuthors` (can you SEE it) and are always FILED against the primary author (`hype_count`/`is_hyped` count rows keyed to `posts.user_id`; a row against the coauthor is invisible AND skips dedupe) — the coauthor gets a push, not a row, and neither author may hype their own collab. Privacy is per author and asymmetric, since the post is the AUTHOR's content and the coauthor is a tag: author `'private'` → only the two of them see it; coauthor `'private'` → the tag and the reach it carries are withheld (`COAUTHOR_VISIBLE`/`COLLAB_REACH_SQL`) but the post stays with the author's circle. Both authors always see their own collab, so every `OWNER_NOT_PRIVATE_SQL` on a post needs the `p.user_id = $1 OR p.coauthor_user_id = $1` exemption (`AUTHOR_VISIBLE_TO_VIEWER`). Only `'private'` withholds — `'friends'` gates workout CONTENT, not identity. A block BETWEEN the two authors ends the collab for everyone (`collabActiveSql`) — never test `coauthor_status = 'accepted'` raw, or the feed keeps showing "a & b" after one blocked the other while the tagged tab has already dropped it. A tag is NOT a grid entry: the coauthor arm of `getUserPosts` is gated on `coauthorOnProfileSql` (per-post `posts.coauthor_on_profile`, else their `tagged_posts_on_profile`, else TRUE) — that gate is grid-ONLY and must never be copied into reach, the Tagged tab or `DIRECT_POST_ACCESS_SQL`, or hiding a post from your own profile starts deleting it from other people's feeds. **`getFeed` and `getUnifiedFeed` carry the same four guards — a merge that reverts one of them silently reopens the leak; ci-smoke's collab section is what catches it.**
- A post that happened-to (mention/comment/collab) must carry its `post_id` in the push `data` — the client opens the post directly via `GET /posts/:postId` (`getFeedEntryForPost`, same projection as the feed). Mentions are in `CAP_EXEMPT_TYPES`: `sendPush` writes the in-app row even when it throttles, so a capped mention reads as "the feature is broken", not as rate limiting. Quiet hours still apply.
- Collab coauthors are tagged IMMEDIATELY (`coauthor_status='accepted'` at insert, Instagram-style) — there is no pending state and no accept step; the exit is `respondToCoauthorInvite(accept:false)`. The create-time push gates on 'accepted' (gating on 'pending' silences it entirely) and is in `CAP_EXEMPT_TYPES`. The "Remove me" notification action is gated per device on `CLIENT_FEATURES.collabTagV1` — an unregistered category renders no buttons.
- Social pushes (comments, mentions, story reactions, coauthor) all gate on `shouldSendNotification(..., "hype")`. Per recipient per comment: mention push replaces the comment/reply push (see `notifyForComment`).
- The Feed UI isn't in the live App Store build and API calls carry no app-version signal. Server-side "user has the feed" = any `posts` row OR `terms_accepted_at IS NOT NULL` (`userHasFeedFeature` in dailyChallengeService) — gate feed-dependent features per-user with it (e.g. the `share_journey` daily challenge).

## Push Notifications
- `device_tokens.environment` selects the APNs host per token (`sandbox` for local DEBUG installs, `production` for App Store/TestFlight); never route pushes solely from server `APNS_PRODUCTION`.
- Hype daily limit did double duty as anti-abuse: dedupe only guards VALIDATED contexts (post, resolvable mile). badge/pr/challenge context_ids and context-less push "hype back" are unvalidated, and `shouldSendNotification` has no rate throttle — so `HYPE_DAILY_ABUSE_CEILING` (hypeService) is their only spam backstop. Keep a ceiling if you make hypes "unlimited".
- `ADD COLUMN ts timestamptz DEFAULT now()` does NOT rewrite the table (PG 11+): the default is stored once as a missing-value, so EVERY pre-existing row reads back the same DDL-time timestamp. Any cron gating on "older than N" therefore stays silent for N and then fires on the entire historical backlog within one tick. Backfill a claim column in the same migration (see 0026's `reminder_sent_at` pre-claim). Also: evaluate per-USER eligibility, not per-row — a new child row with a NULL claim re-qualifies a user who is mid-cooldown.
- ...but a backfill only belongs in a migration when it's SMALL. Migrations run at BOOT over the shared pool, which pins `statement_timeout` AND node-pg `query_timeout` to 30s (DbService), one transaction each: a statement that overruns aborts the migration, never records it, and retries every boot — a boot loop, with no shell access to escape. Table-rewriting backfills and `CREATE INDEX CONCURRENTLY` go in a post-`listen()` background task on a dedicated no-timeout client (`db/backfillFeedRoles.ts`), keeping the migration itself metadata-only (constant default, `CHECK ... NOT VALID`) and the new column's pre-backfill value equal to today's behaviour.
- Push `data` values must be STRING-valued: shipped builds decode the inbox's `data` as `[String: String]`, so ONE number/bool in a new payload breaks the entire inbox decode client-side. The inbox list enriches rows at read with `actor`/`post_preview` — previews authorize via `visiblePostPreviews`, which shares `DIRECT_POST_ACCESS_SQL` with `visiblePostAuthors` (never fork that guard), and the response must stay wrapped in `signMediaUrlsDeep`.
- Server deploys land well before an App Store release, and some users never update. Anything a current shipped client can't handle is gated PER DEVICE, not per deploy: the app declares capability strings at `POST /devices/register` (`device_tokens.client_features`) and the server checks `userSupports`/`supportsClientFeatureSql` (`clientFeatures.ts`). Add a string only in the build that implements it, never reuse one. Env flags stay as kill switches (default off), never as the safety mechanism — an env flag can only answer "is the new build out?", which is the wrong question. An APNs `badge` is why: an older build has no code that clears it, so a server-set badge is a permanently stuck red dot.

## ESM Reminder
All imports MUST end with `.js` extension, e.g. `import { foo } from './services/fooService.js';`
