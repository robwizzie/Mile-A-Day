# Website Conventions

## Stack
- Next.js 16 App Router (single-page marketing site)
- React 19, Tailwind CSS 4 (via `@tailwindcss/postcss` plugin)
- Deployed on Vercel with `@vercel/analytics`
- Icons: `lucide-react`
- Animations: `tw-animate-css` + custom keyframes in globals.css (Motion block at the end)

## Structure
- `app/` - Next.js App Router (layout.tsx, page.tsx, globals.css)
- `components/` - Page sections (navbar, hero, features, CTA, footer, etc.)
- `public/` - Static assets (images, favicons)
- Single page site: `page.tsx` composes section components in order.

## Package Manager
Use `npm` for all operations.

## Tailwind CSS 4
- No `tailwind.config.js` - Tailwind 4 uses CSS-based configuration.
- Theme tokens and custom properties defined in `globals.css` via `@theme` directive.

## Styling Patterns
- Home order is the conversion path (comment in `app/page.tsx`): hero → `LiveStatsBand` → `HowItWorksSection` → `PanelCarousel` (`featureSlides()` + `CompetitionsSection fill`, one swipeable band with tab pills, autoplay only on screen and until touched, `/#<slide key>` opens a slide) → `HabitSection` → `WhatsNewSection` → `StorySection` → `SupportSection` → `DeskTeaserSection` → `CtaSection`. Those sections and their headings ("The miles are adding up.", "Dead simple. By design.", "66 days to build a habit.", "It started with a stupid bet.", "Need a hand?", "Your streak starts today.") are the owner's; restyle, never drop or rewrite them.
- The theme borrows the App Store screenshots without copying them: hero + a curated few `PanelBand`s (`components/feature-panels.tsx` `PANELS`, phones cut from `marketing/app-store/<version>/` into `public/images/app-store/`); every other section uses `SectionHeader` (eyebrow, heading, line) on alternating dark (`#0e0809`/`#140b0e`) and cream (`#f6f1ec`) bands, with solid colour cards in the screenshot palette.
- Fonts: Inter (body, `--font-body`) and Inter Tight 800 (headings, `.font-heading`, `--font-display`) via `next/font/google`. Headlines are sentence case ending in a period, never all caps; eyebrows are small tracked caps. The OG cards keep their own vendored fonts.
- Show only REAL app captures and REAL data: phones are `Phone` cutouts of the App Store screenshots, numbers come from `/public/*`; never hand-build an imitation of app UI (mock leaderboards, sample stat tiles, invented values).
- Colour comes from the screenshot palette: a section's `PanelBand` from/to, the one red `#ec3047`, or (the stats band's `LOOKS`, one screenshot colour + lucide icon per stat) a tile in one of those colours. No glass cards, glow blobs, icon-chip grids or marquees; buttons are solid pills (`AppStoreButton`, red `.glass-button`, white secondary) with the `.lift` hover. The legacy `.glass-*`/`.hero-gradient` classes in globals.css are flattened to this look, so every page shares it.
- Motion: mark elements `data-reveal` (`"phone"` climbs, `"pop"` scales; stagger with `--d`) and `RevealObserver` (root layout) eases them in once; the hero plays `mad-rise`/`mad-phone-in` on load. Hidden states live only under `html.reveal-on`, which Reduce Motion never gets, so content is never stuck invisible. Count-ups start on screen via `useInView` (callback ref). Never give a client component's props a server component's icons: shared lists like `ReleaseFeatureList` live in a file without "use client".
- Every page renders `Navbar` + `Footer` (the 404 is the hero red with `LostFlamey`, the app's real `FlameyPack` stickers in `public/images/flamey-pack/`); profile medals are `HangingMedal` (`components/medal.tsx`, a port of the app's `MedalView`/`MedalRibbon` geometry and `MedalPalette`).
- In-page links (`/#support`, `/#features`) land via `HashLander` (root layout: re-aims while the page settles, yields to the visitor's own scroll); sections carry `scroll-mt-*`, and anything above them must reserve its height before data arrives. Our story is its own page, `/story` (navbar + footer link there; Instagram posts = `INSTAGRAM_POSTS` in `lib/story.ts`, embedded lazily by `InstagramPosts`).
- Click labels: App Store buttons send `app_store:<place>` (`AppStoreButton place=`; backend counts every `app_store%`), other key buttons a `data-track` name; add new ones to `TARGET_LABELS`/`PLACE_LABELS` in the admin `Website.tsx`.
- Search/AI: the `FAQ` in `support-section.tsx` also feeds the home page's FAQPage JSON-LD and `/llms.txt` (`app/llms.txt/route.ts`, built from `FAQ` + `CURRENT_RELEASE`); keep answers factual and change them in that one place.
- Copy is plain and specific, written like a person: no em dashes, no "seamlessly"/"everything you need" filler.
- Primary color: `#c72554` (burgundy red); the hero/CTA red is the screenshots' `#ec3047`→`#dc253b`.

## Admin dashboard (`app/admin/`)
- Tabs render from the `TABS` array in `dashboard.tsx`; each tab is one file in `_components/`. Data goes through `getData("<path>")` → the same-origin proxy → backend `/admin/<path>`, so a new panel needs a backend route and nothing else.
- `_components/theme.ts` ports the app's `MADTheme.swift` — madRed, walkBlue, the 16px/5%-fill/8%-border card, SF Rounded (`ui-rounded`, Nunito fallback, loaded in `admin/layout.tsx`). Never hand-pick a colour: if it isn't in MADTheme it's a new brand colour. Workout types use `workoutColor()` (runs red, walks blue). The PAGE stays black, deliberately — the app's red-tinted ground pushes colour into every neutral, which a metrics screen can't afford.
- Spacing is three tokens, not a per-card guess: `STACK_SECTIONS` between subjects, `Section` for the header above a group, `gap-3`/`gap-5` inside grids. Everything was `space-y-6` once, which is why a stat grid and a whole new subject looked equally far apart.
- A delta must describe the number it sits on — same quantity, same window. A "today" figure with a 30-day delta, or a signups delta on a total-users count, reads as precision and means nothing. Under ten in the prior window `Delta` shows the absolute change, because "+200%" off one event is noise.
- Retention is TWO readings of one clock: the weekly cohort grid and the D1/D7/D30 marks (`RETENTION_MARK_WINDOWS`, BRACKETS of days since the signup's ET day — a daily-mile app can't demand the exact day). Both measure a COUNTING workout from the signup's ET calendar day; a mark on a different clock than the grid reads as two dashboards disagreeing. Seeded in `admin-analytics-check` by `adm-ret`, whose walks sit outside the 30-day trend window on purpose.
- A metric that counts PEOPLE is `distinct` in `TREND_SPECS` and needs a `windowTotal` — summing its daily values counts somebody active on ten days as ten people, which once printed a number larger than the whole user base. Its bars stay a shape, never addends.
- `HeatGrid` only takes `fit` (stretch to the card) because its header labels are absolutely positioned; put a label back in the flow and flexible tracks drift off their cells again.
- Multi-series charts use `SERIES` (validated on the app surface: CVD separation, contrast, one lightness band). Assign in order, never cycle it, and never add a 4th concurrent series — walkBlue and warning are too light to join that band, so split the chart instead. `PALETTE` is for one-series-per-card breakdowns only.
- One person is `UserModal` (Overview · Friends · Posts), fed by `users/:id`, `users/:id/friends` and `users/:id/posts`. Every name on it is a `PersonButton` that opens a STACKED `UserModal` (`backTo` + `hint`), so closing returns to the list; a new per-person panel is a tab there, never a second modal. The acquisition block is the per-user face of the referral graph: `referredBySql` (adminService) is the ONE reverse lookup and shares `referralHandleSql` with the graph, so "who referred whom" answers the same from every panel.
- Any number worth reading is worth opening: panels call `useDrilldown()({kind, id})` for the rows behind it and `useOpenUser()` for one person, both from `Drilldown.tsx`. A new drill-down is a `DRILLDOWN_KINDS` entry plus a case in `getDrilldown` — no new endpoint, no new drawer.
- A `HeatGrid` needs FIXED px columns and `justify-content: start`. A label placed in the flow widens its own track (the axis then drifts off the cells), and an `auto` first track in a stretched grid absorbs all slack and floats the plot to the right edge.
- Photos ≠ posts: `is_auto` route cards are published FOR a user who skips the prompt, so any "is the social feature working" number reads `photo_count`, never `post_count`.
- `Section`/`Card` headers wrap on CONTENT, never a breakpoint. Their `actions` slot usually holds a `SegmentedControl`, which is ONE nowrap line of pills — 805px for the 7-metric Trends one — so a `shrink-0` actions div takes that width off the top and the title column collapses (64px, one word per line) while the DOCUMENT, not the card, goes 899px wide on a 390px phone: horizontal scroll on every tab, cards looking clipped, and raising the page gutter does nothing. `flex-wrap` + `basis-72` on the title drops the control to its own full-width line only when it truly won't fit; `min-w-0` is what lets a hint wrap at all. Verify by MEASURING `document.documentElement.scrollWidth` against the viewport, not by reading the JSX — the admin dashboard renders end-to-end offline with a `mad_admin` cookie (presence is the only gate) and Playwright `route()` mocks on `/admin/api/data/**`.
- The Network tab (`Network.tsx` + `NetworkWeb`/`NetworkTree`/`NetworkMap`, shared hooks in `networkCanvas.tsx`) draws on CANVAS under one camera (world units, text back in screen px) — an SVG redrawn per force-simulation tick can't hold frame rate at thousands of nodes. A canvas wrapper gets `flex-1` only on the ROW axis (`lg:flex-1`, or full screen): in the phone column a flex-basis of 0 overrides its fixed height and the canvas collapses to nothing — the web and the map both rendered as bare side panels at 390px until measured. Verify a canvas by reading pixels (`getImageData` in `page.evaluate`) and weight brightness by ALPHA: canvas pixels aren't premultiplied, so the 5% land fill reads as pure white.
- The Website tab (`Website.tsx`, backend `GET /admin/web`) reads `web_events`, written by `SiteTracker` (root layout: a view per pathname, clicks via one capture listener; App Store links → `app_store`, `data-track` overrides the label; skips `/admin`, `/users`, DNT/GPC). Never add a cookie or stored id to it; a click worth naming gets `data-track`.
- A colour skin's preview draws his BODY from code (`lib/flamey/flameyBody.ts` + `paletteFx.ts`, ports of FlameBuddyFigure/FlameyPalettes, still/healthy/legs/rest arms) in its `palette`, never the plain PNG; `FlameyStage` does it before `composeLook(figure: false)`. Change them with the Swift.
- The Skin Builder (`/admin/skins`) draws with `lib/flamey/skinRender.ts` + `compose.ts`, which `app/FlameyExport/convert/match.mjs` also loads through Node's `stripTypeScriptTypes`: keep them erasable TS (no enums/namespaces) with relative imports only (no `@/`), and re-run match.mjs after changing them. Skins come from `/admin/api/skins` (backend `GET /flamey/skins`); only `next dev` falls back to `../backend/flamey-skins`.

## SEO / link previews
- Every unfurl card draws from `app/_og/shared.tsx` (vendored Bebas Neue + DM Sans `.woff` — Satori can't read woff2 or next/font — the app icon, a pre-cropped dashboard shot, `PersonCard`). A page that sets its own `openGraph`/`twitter` REPLACES the root object (no merge) and LOSES the root card image: restate title/description/url and give the segment an `opengraph-image` (re-exporting the root one is enough — see `privacy/`). Profile/post cards show only what `/public/users/:username` already publishes. Check rendered tags with `next start` + curl and LOOK at each PNG.
- Every page with a card also has an `og.mp4` route: a scene in `app/_og/video/scenes/`, served by `ogVideoResponse` (keyed by `factsKey` of what it draws, never raw params), tagged via `ogVideos()` in the page's `openGraph.videos`; the PNG stays og:image. ONE payoff per clip, everything landed by ~3.5 s then held still to read; no ambient sparkles, shine sweeps or bobbing. Keep moving pixels small (backgrounds still, `foreground()` for the loop fade), clips ≲1.2 MB, and look at the frames before shipping. Details: docs/conventions/website.md § Link-preview videos

## Release notes
- `lib/releases.ts` is the site's copy of the app's `WhatsNewCatalog` (newest first): adding a release there moves the home page's "New in" section, `/updates`, the hero pill, the footer's version and the JSON-LD `softwareVersion` together. Version = the App Store MARKETING_VERSION that shipped it. Support email lives once in `lib/site.ts`.
- What's New screenshots are `RELEASE_SHOWCASE[version]` in `lib/releases.ts` (`title` = a feature title), real captures only, at `public/images/whats-new/<version>/`; `screenshot: null` hides the slot. The home section's dropdown walks `RELEASES`; `/updates` draws the same shots per release. Save captures as WebP (q82, ~50 KB) and render them `unoptimized`: the optimizer's first-hit AVIF encode of a 776×1680 PNG is what made the carousel slow. A replaced image gets a NEW filename (CDN/optimizer caches key on the path). `ShowcaseCarousel` inside a grid needs a `minmax(0,1fr)` column, or the track's full width becomes the column's min-content.
